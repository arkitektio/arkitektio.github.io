This guide takes you from an empty folder to an app whose actions you can call from Orkestrator. It
assumes you have [installed arkitekt](/docs/developers/python/installation) and have a server to
connect to. Read [Core concepts](/docs/developers/python/concepts) first if the words *action*,
*agent* or *task* are unfamiliar.

## 1. Scaffold the project

In a new, empty folder run:

```bash
arkitekt init
```

The command asks for an identifier, an author and the name of the entrypoint file, then writes
`app.py` from a template. With `uv` installed it also runs `uv init` and `uv add "arkitekt[all]"`,
so the project gets its own environment and a `pyproject.toml`.

To skip the questions:

```bash
arkitekt init my-app --identifier com.example.myapp --version 0.1.0 --template simple --yes
```

| Option | Meaning |
|---|---|
| `PATH` | Sub-directory to create the app in (default: the current directory) |
| `--identifier`, `-i` | A unique identifier, ideally in reverse-domain form (`com.example.myapp`) |
| `--version`, `-v` | Semantic version (default `0.0.1`) |
| `--author` | Shown to users of the app (default: your OS user) |
| `--entrypoint`, `-e` | The entrypoint file without `.py` (default `app`) |
| `--template`, `-t` | `simple` (strings and a generator) or `filter` (signal processing on lists of floats) |
| `--package-manager`, `-pm` | `uv` (default if installed) or `pip` |

There is **no manifest file**. The identity you entered is written into `app.py` as the arguments
of `App(...)`, and that code is the single source of truth. To change the version later, edit the
file.

## 2. Read the generated app

The `simple` template produces something like this (docstrings shortened):

```python
import time
from typing import Generator

from arkitekt import App, run

app = App("com.example.myapp", "0.1.0", author="jane")


@app.action
def generate_n_string(n: int = 10, timeout: int = 2) -> Generator[str, None, None]:
    """Generate N Strings

    Generates {{n}} strings with a {{timeout}} second pause between each.
    """
    for i in range(n):
        time.sleep(timeout)
        yield f"Hello {i}"


@app.action
def append_world(hello: str) -> str:
    """Append World

    Appends " World" to {{hello}}.
    """
    return hello + " World"


if __name__ == "__main__":
    run(app)
```

- `app = App(...)` **declares** the app. Importing this module connects nothing, so the CLI, tests
  and packaging can all import it safely.
- Each `@app.action` becomes an action on the platform. `generate_n_string` is a generator, so its
  action **streams**: each `yield` reaches the caller as it happens.
- `run(app)` connects and serves until you stop it. The `if __name__ == "__main__"` guard means
  `python app.py` works too, but the CLI is the better way to run it while developing.

<Callout type="warn" title="Keep module import side-effect free">

The CLI imports your module to find the app: when running, when inspecting and when building the
container. Opening a device, loading a model or connecting to anything at module level would
happen every time. Put such work in an [`@app.startup` hook](/docs/developers/python/state-lifecycle)
instead. `arkitekt inspect variables` warns about module-level variables that would leak across hot
reloads.

</Callout>

## 3. Run it in development mode

```bash
arkitekt run dev
```

On first run a browser opens and asks you to authorize the app on your server. After that you
should see the agent connect and register two implementations. Edit `app.py` and save: the app
**reloads** and re-registers, without you restarting anything.

| Option | Meaning |
|---|---|
| `--url`, `-u` | The server (otherwise `$FAKTS_URL`, then the public deployment) |
| `--headless` | Print a device code instead of opening a browser |
| `--no-cache` | Forget the cached credential and authenticate again |
| `--deep` | Watch the whole directory tree for changes, not only the entrypoint |
| `--log-level`, `-l` | e.g. `DEBUG` |
| `--context module:attr`, `--context-file path` | The [app context](/docs/developers/python/state-lifecycle#app-context), if the app declares one |

`arkitekt run prod` runs the app the way it runs inside a container: no reloading. Use it to check
the app before [packaging](/docs/developers/python/build).

<Callout type="info" title="Which app does the CLI run?">

The CLI looks for the app like uvicorn does. The default target `app` imports the module `app` and
uses its variable `app`, or its only `App`. Pass `arkitekt run dev pkg.main:api` or set
`ARKITEKT_APP=pkg.main:api` to point it somewhere else.

</Callout>

## 4. Call it

Open Orkestrator, find your app under **Apps**, and open `Append World`. The form was generated
from the signature: one text field called `hello`. Run it, and a **task** appears. Its result,
logs and progress stream in from your agent.

Run `Generate N Strings` and you will see each yield arrive one by one. If the process is killed
while a task runs (try `kill -9` on it), the task ends as **LOST** once the grace window has passed.
The platform knows the agent died, and that it cannot know whether the work finished. [Durable execution](/docs/developers/python/durable-execution)
explains what you can do about that.

From a terminal, `arkitekt call remote` calls an action of the app through the server, which is
handy in scripts and CI.

## 5. See what the app registers

```bash
arkitekt inspect all --pretty          # everything: implementations, states, requirements, bloks
arkitekt inspect implementations       # one entry per action, with its ports
arkitekt inspect requirements          # the services the app needs
arkitekt inspect lifecycle             # startup, shutdown and background hooks
```

`inspect` never connects. It shows exactly what `run` would register and validates it the way the
server would, so it is a good check in CI. The packaging step runs it inside the built container too.
