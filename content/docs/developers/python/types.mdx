The type annotations on an action are its contract. They decide which values a caller may pass,
which widget Orkestrator shows, which actions can be wired together in a workflow, and how each
value is transported. This page goes through the kinds of types in increasing order of weight.

<Callout type="info" title="The rule">

A port may only name a type the app knows. The built-in scalars and containers are always known.
Everything else must come from a service the app declares, `@app.model`, `app.register_structure`
or `app.memory_structure`. An unknown type is rejected when the action is **declared**, so you find
out when the module is imported rather than when someone calls the action.

</Callout>

## Scalars and containers

`str`, `int`, `float`, `bool` and `Enum` subclasses travel as values. So do `list[...]`,
`dict[str, ...]`, `Optional[...]` (a nullable port) and `Union[...]`. A function that returns a
tuple has one output port per element.

```python
from enum import Enum
from typing import Annotated, Optional
from arkitekt import App, Description

app = App("filters", "0.1.0")


class Mode(Enum):
    MEAN = "mean"
    MEDIAN = "median"


@app.action
def smooth(
    values: list[float],
    window: Annotated[int, Description("Samples to average over")] = 3,
    mode: Mode = Mode.MEAN,
    label: Optional[str] = None,
) -> tuple[list[float], float]:
    """Smooth

    Smooths the signal and returns it with its new maximum.
    """
    ...
```

## Models: records by value

A class decorated with `@app.model` becomes a record whose fields are ports. Use it when an action
returns several named values that belong together:

```python
from arkitekt import App, Task

app = App("measure-nuclei", "0.1.0")


@app.model
class NucleiMeasurement:
    """What a segmented field of nuclei amounts to."""

    count: int
    mean_area_px: float
    covered_fraction: float


@app.action
def measure_nuclei(min_size: int = 20, *, task: Task) -> NucleiMeasurement:
    """Measure Nuclei"""
    ...
    return NucleiMeasurement(count=12, mean_area_px=140.0, covered_fraction=0.08)
```

The class becomes a dataclass if it is not one already. Models may contain other models, and they
always travel **by value**, so keep them small.

## Service structures: large data by reference

Images, volumes, traces and tables are too big to send through a task. They live in a data service
(for images, [Mikro](/docs/design/services/mikro), backed by a database and an S3-compatible object
store), and **only a reference travels**. The receiving agent resolves the reference with its own
client. This is what Arkitekt calls a [structure](/docs/design/terminology/structure).

A service brings its structures with it. Declare the service, and its types become valid ports:

```python
from typing import Annotated

import numpy as np
import xarray as xr
from scipy import ndimage

from arkitekt import App, Description, Task
from mikro import Mikro, mikro_service
from mikro.arkitekt.specs import Volume, ensure

app = App("denoise-volume", "0.1.0", services=[mikro_service])


@app.action
def denoise(
    volume: Annotated[Volume, Description("The stack to smooth")],
    sigma: Annotated[float, Description("Gaussian width, in pixels")] = 1.5,
    *,
    mikro: Mikro,
    task: Task,
) -> Volume:
    """Denoise Volume

    Smooths a stack with a gaussian and stores the result on the same grid.
    """
    source = volume.data  # a lazy xarray, backed by the object store
    task.progress(20, f"Smoothing {source.shape}")

    smoothed = xr.DataArray(
        ndimage.gaussian_filter(np.asarray(source), sigma=sigma), dims=source.dims
    )
    task.progress(70, "Uploading")

    result = mikro.create_array_dataset(
        data=smoothed,
        scales=[],
        name=f"denoised (sigma={sigma})",
        axes=volume.carried_axes(smoothed.dims),
        derived_from=[volume.derive_identity(value_relation="TRANSFORMED")],
    )
    return ensure(result.lens(), Volume)
```

The example shows four things:

- **`Volume` is a spec, not a new class.** Mikro stores array datasets. A *lens* is a view on one of
  them. `Volume` (from `mikro.arkitekt.specs`) is a lens annotated with a requirement: exactly three
  spatial axes. As an argument, it lets Orkestrator and the workflow editor offer only datasets that
  fit. As a return type, it tells the platform what the action produces. Related specs include
  `Image`, `SingleChannelImage`, `MultichannelVolume`, `TimelapseVolume` and `LabelMask`.
- **`volume.data` is lazy.** It is an `xarray.DataArray` backed by zarr in the object store. Slicing
  it downloads only the chunks you touch. `np.asarray(...)` loads what is left.
- **Results are written with the client, not returned as arrays.** `mikro.create_array_dataset(...)`
  uploads the array and creates a dataset. `derived_from=[...]` records a derivation edge, so the
  provenance graph knows the output came from the input and, here, that both share a grid.
- **`ensure(lens, Volume)` checks the promise.** It raises if the result is not actually a volume,
  instead of returning something that silently breaks a downstream action.

<Callout type="warn" title="Local objects are not live">

The objects a client returns are snapshots. Setting an attribute on one changes nothing on the
server. To change the stored object, call the matching mutation on the client.

</Callout>

## Your own structures

When two apps share a Python library that defines a type, and the objects live somewhere both can
reach, register the type as a structure. Pick an identifier (`@package/key`), and give an
**expander** that turns an id back into the object. The expander receives clients by annotation,
the same way an action does:

```python
from arkitekt import App
from mikro import Mikro, mikro_service

from mylib import Thing   # a class both apps import

app = App("things", "0.1.0", services=[mikro_service])


async def expand_thing(id: str, mikro: Mikro) -> Thing:
    return Thing(await mikro.aget_file(id))


app.register_structure(Thing, "@mylib/thing", expand=expand_thing)
```

By default the structure is *shrunk* to its id by reading `.id`. Pass `shrink=` if yours differs.
The identifier is a contract with every other app that handles this type, so don't change it
casually.

## In-memory structures

Sometimes the data is scratch: an array passed from `read_tiff` to `segment` to `count_objects`
inside one pipeline, not worth storing. `app.memory_structure(cls)` declares a type whose instances
**stay on the agent**. Only a reference travels, and the next action on the same agent gets the
object back:

```python
import numpy as np

from arkitekt import App

app = App("in-memory-pipeline", "0.1.0")
app.memory_structure(np.ndarray, description="A numpy array held by this agent")


@app.action
def threshold(image: np.ndarray, cutoff: float = 0.5) -> np.ndarray:
    """Threshold"""
    return image > cutoff


@app.action
def count_pixels(mask: np.ndarray) -> int:
    """Count Pixels"""
    return int(mask.sum())
```

Annotate ports with the registered class itself (`np.ndarray`). A generic alias such as
`numpy.typing.NDArray[Any]` is a different type annotation and is not matched to the
registration.

In-memory references are only meaningful on the agent that holds them. They are gone when that
process ends, and they cannot be resolved by another app. Anything worth keeping belongs in a data
service.

## Choosing

| You have… | Use |
|---|---|
| a number, a string, a flag, a choice | a scalar or an `Enum` |
| a few named values that belong together | `@app.model` |
| images, volumes, traces, tables | the service's structures (`mikro`, `elektro`, …) |
| a shared library type stored somewhere both apps reach | `app.register_structure` |
| intermediate data between actions of one agent | `app.memory_structure` |
