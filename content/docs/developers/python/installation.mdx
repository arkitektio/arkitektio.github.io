## Install

```bash
pip install "arkitekt[all]"
```

This installs the `arkitekt` command line interface, the runtime and every service client. It is the
right choice when you are building an app and are not yet sure what you need. `arkitekt` requires
**Python 3.11 or newer**.

With [uv](https://docs.astral.sh/uv/):

```bash
uv add "arkitekt[all]"
```

## Extras

The CLI and the packaging tooling are always included. Everything else is an extra, so a library
or a container image can pull in only what it uses:

| Extra | Brings in |
| --- | --- |
| `rekuest` | The distributed runtime. **Required to offer actions with `run(app)`.** |
| `mikro` | Microscopy and imaging data |
| `elektro` | Electrophysiology data and simulations |
| `kraph` | Knowledge graphs and measurements |
| `fluss` | Workflows, and the engine that runs them |
| `kabinet` | Managing deployments of apps |
| `unlok` | Users, clients, hubs and redeem tokens (Lok) |
| `alpaka` | LLMs and chat |
| `lovekit` | WebRTC streams and rooms |
| `serve` | Serving an app from a FastAPI application |
| `qt` | Qt integration (`arkitekt.qt`) |
| `tqdm` | A `tqdm` that reports progress to the running task |
| `mesh` | Joining the deployment's private mesh from inside your process |

```bash
pip install "arkitekt[rekuest,mikro]"
```

Declaring an app, inspecting it, packaging it and calling services with `easy` need no runtime.
Only `run(app)` does. Without the `rekuest` extra it raises `RuntimeNotInstalledError`, which
tells you what to install.

## Connecting to a server

Nothing connects when you import `arkitekt` or declare an `App`. The connection is made when you
call `run(app)` (to offer actions) or enter `easy(...)` (to call services). Both look for the server
in this order:

1. the `url=` argument, e.g. `run(app, url="http://localhost:7080")`;
2. the `FAKTS_URL` environment variable;
3. the public deployment.

The first time an app connects, a browser opens and asks you, as a member of an organization on that
server, to authorize the app. The credential is cached locally, so later runs connect without
asking (pass `no_cache=True`, or `--no-cache` to `arkitekt run dev`, to authenticate again). On a machine without a browser, pass `headless=True` (or
`--headless` on the CLI). The device code is then printed and can be approved from any other
device.

| Variable | Used for |
|---|---|
| `FAKTS_URL` | The server to connect to |
| `FAKTS_TOKEN` | A previously issued credential (`client_id:refresh_token`), for unattended runs |
| `FAKTS_REDEEM_TOKEN` | A redeem token that provisions the app without a person approving it |
| `ARKITEKT_MESH`, `ARKITEKT_MESH_PROXY` | Whether and how to reach services that are only on the [mesh](/docs/design/security/mesh) |

The connection flow itself is described in [Service discovery](/docs/design/architecture/service-discovery).

## Check the install

```bash
arkitekt self version    # the installed arkitekt version
arkitekt self info       # versions of every Arkitekt package, the package manager, paths
```

## Migrating from arkitekt-next [#migrating-from-arkitekt-next]

`arkitekt` replaces the `arkitekt-next` package. The concepts are the same, but an app is now
declared explicitly instead of being assembled from module-level decorators.

| arkitekt-next | arkitekt |
|---|---|
| `pip install arkitekt-next` | `pip install arkitekt` |
| `from arkitekt_next import register` + `@register` | `app = App("name", "0.1.0")` + `@app.action` |
| `from rekuest_next …` | `from arkitekt import …` (rekuest is an implementation detail) |
| `from mikro_next.api.schema import Image` | `from mikro import Mikro, mikro_service` and the lenses in `mikro.arkitekt.specs` (`Volume`, `SingleChannelImage`, …) |
| `easy("name")` as an app you register on | `App(...)` + `run(app)` to offer; `easy("name", service)` only to call |
| `@startup`, `@background`, `@state`, `@context` | `@app.startup`, `@app.background`, `@app.state`, `@app.context` |
| module-level `log(...)`, `progress(...)` | `task.log(...)`, `task.progress(...)` on an injected `task: Task` |
| `find(...)` / `call(...)` inside an action | an `@app.declare` protocol, called from an `@app.workflow` |
| `arkitekt-next init`, `arkitekt-next run dev` | `arkitekt init`, `arkitekt run dev` |
| `arkitekt-next kabinet build/stage/publish` | `arkitekt plugin build/stage/publish` |
| `.arkitekt/manifest.yaml`, `arkitekt manifest …` | no manifest file: the app declares itself, `arkitekt inspect all` shows what it registers |
| `app.register_blok(...)` with `jsx(...)` | `app.blok(...)`, with `bsx(...)` if you want to parse ahead of time |

<Callout type="warn" title="effects= changed meaning">

If you used `effects=` on an action to attach UI effects to ports, that argument is now called
`port_effects=`. `effects=` now takes an [`Effects`](/docs/developers/python/durable-execution#effects)
claim about what running the action again would do.

</Callout>
