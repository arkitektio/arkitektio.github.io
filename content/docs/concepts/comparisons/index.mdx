These pages explain why Arkitekt is built the way it is, by comparing it with tools that made other
choices. They are not a ranking. Each tool fits its own kind of work.

<Callout type="info">

If you think we misrepresent a tool, or that Arkitekt should do something differently, please open
a thread on [GitHub Discussions](https://github.com/orgs/arkitektio/discussions).

</Callout>

## Why not Kafka? [#why-not-kafka]

Kafka is a distributed, replicated commit log, built for high-throughput data pipelines. It keeps
messages for a long time and is run as a cluster of brokers.

Arkitekt needs something else from its messaging:

- **Low latency over high throughput.** In a live experiment the time from stimulus to response is
  short, so a single task has to reach its agent fast. Kafka is tuned for volume, and RabbitMQ-style
  queues reach lower latency for single messages.
- **Small messages.** Large data stays in the data services and only references travel, so a message
  is a task, a progress report or a result id.
- **Easy to run on one machine.** Arkitekt has to start on a laptop. Kafka is only configurable as a
  distributed system with several broker instances.

Older versions of [Rekuest](/docs/develop/internals/rekuest) queued tasks through RabbitMQ for these
reasons. Today tasks are rows in Postgres, Redis carries the queues to connected agents, and
Rekuest's Rust backend, takt, holds the agent connections. Durability comes from the agent's journal
and the task history in Postgres (see [Durable execution](/docs/develop/patterns/durability)), so
there is no need for a separate log.

## Why not REST? [#why-not-rest]

Arkitekt's services speak GraphQL. Bioimage data is highly relational, and GraphQL lets a client ask
for exactly the slice of that graph it needs in one strongly typed, self-documenting query, with
subscriptions for live updates. The full argument, with examples you can run against your own
server, is in [GraphQL: Why we like GraphQL](/docs/develop/internals/graphql#why-we-like-graphql).
To write a client, see [Developing with GraphQL](/docs/develop/python/graphql).

GraphQL also brings problems that REST does not have:

| Problem | What it means | What Arkitekt does |
|---|---|---|
| Learning curve | Harder to pick up than REST | Typed code generated from the schema ([turms](https://github.com/jhnnsrs/turms) for Python, graphql-codegen for TypeScript) |
| Caching | A query is not a URL, so plain HTTP caching does not fit | Mitigated per service, but still needs care |
| N + 1 queries | A nested query can trigger one database query per item | Dataloaders, and the Strawberry-based servers' query optimizer |
| Expensive queries | A client can write a query that overloads the server or denies service | Query complexity analysis and rate limiting |
