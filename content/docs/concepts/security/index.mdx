Security, privacy and performance are not separate concerns in Arkitekt, they are
three faces of the same design goal: keeping you in control of your data while
still letting you move fast. This section pulls that story together.

<Callout type="info" title="We don't want your data">

Arkitekt is a **middleman**, not a data silo. When you run your own instance, the
data stays on infrastructure *you* control and we never see it. The parts of the
platform that *do* touch personal data are kept to the bare minimum, and are
described in full in the [Privacy Policy](/docs/privacy).

</Callout>

## The trust model in brief

- **Everything is authenticated and authorized.** See [Security
  Measures](/docs/concepts/security#security-measures).
- **The organization is the hard boundary.** See
  [Organizations](/docs/concepts/terminology#the-hard-boundary).
- **Open by default, *within* your organization**, with role-based access control
  on top. See [Open by
  default](/docs/concepts/terminology#open-by-default-within-your-organization).
- **You and the machine stay distinct.** How an agent's work is attributed is
  described in [Provenance & Audit Logging](/docs/concepts/provenance).

## Honest limits

We would rather be upfront than oversell. Arkitekt is powerful, but it is also
young, and a few things are still works in progress:

<Callout type="warn" title="Arkitekt is early-stage software">

- We currently **discourage multi-user production deployments**; see [the
  production readiness of Arkitekt](/docs/concepts/planning).
- Some of the more powerful remote features (online monitoring, remote control)
  are best run behind a **VPN** for now. See [Using a VPN](/docs/concepts/security/mesh#arkitekt-through-a-vpn).
- **Scope-based access control is not yet fully enforced**; see
  [Scopes](/docs/concepts/security/identity#scopes).
- Data on the public **`demo.arkitekt.live`** instance is stored **unencrypted**,
  treat it as public; see the [Privacy Policy](/docs/privacy#tier-4-demoarkitektlive).

</Callout>

## Security Measures

### Why Security is Important

While we believe a majority of scientist are good actors, there is always a risk of encountering bad actors. But even if we assume that all users are good actors, some of your data may be sensitive and should be protected. Also, as a platform for other developers to build on, and given the nature of accidental bugs in scientific software we need to ensure that the platform is secure, and that a random plugin does not delete your whole
database.

### Security Measures

**Everything is authenticated and authorized** - Every request to the Arkitekt API is authenticated and authorized. This means that every request must be made by a user who is logged in and has the correct permissions to make that request, there is no way to make a request to the API without being authenticated and authorized.

**Apps only have access to the data they need** - When you create an app in Arkitekt, you can specify the permissions that the app needs. This means that an app only has access to the data it needs to function, and nothing more. No app can spy on your data and send it to a third party.

**Plugins are sandboxed** - Plugins run in a sandboxed environment, which means that they can't access the data of other plugins or your filesystem. This means that you can install plugins without worrying about them accessing your data or potentially damaging your system. They only
can interact with our protected APIs.

**Transport Layer Security (TLS)** - When hosting your own Arkitekt instance, you can enable TLS to encrypt the data that is sent between the client and the server. This means that even if someone intercepts the data, they won't be able to read it. Which ports the hub exposes, including the HTTPS port, is listed in the [installation guide](/docs/reference/requirements).

**Multi-user support** - Arkitekt supports multiple users with their own data and roles, isolated per [organization](/docs/concepts/terminology#organization).

**Admin configuration** - Arkitekt provides a variety of configuration options, that allow administrators to configure the system to their needs. This includes the ability to configure apps, plugins, and the system itself remotely. Do you want all users that use Napari to be blocked from using the system on a certain day? You can do that.

**Data restoration** - Newer Arkitekt services have audit logs, that allow administrators and users to see what has been done to their data and by whom (and by what app or plugin). For most actions, you can also revert the action, restoring the data to its previous state.

### User Management & Multi-Tenancy

Every Arkitekt server ships with a multi-tenancy system at its core: a single deployment can host multiple **organizations**, each with its own users, data, and configuration, fully isolated from one another. Within an organization access is open by default, with role-based access control to tighten it where you need to. What an organization is, why it is the hard boundary, and how the defaults work is described in [Organizations](/docs/concepts/terminology#organization).

### You and the Machine

Security and access control are only half of the story. The other half is **provenance**: knowing, with certainty, who did what to which piece of data. This has become urgent now that AI agents routinely act inside our systems, and Arkitekt therefore keeps a deliberate, first-class distinction between **you** and **the machine**, even when the machine is acting on your behalf. We consider this non-negotiable: scientific provenance only means something if it is honest about its sources, and handing work to an agent should never cost you the ability to say, later and with confidence, how a result was really made.

For how this audit trail is recorded, attributed, and queried in practice, see [Provenance & Audit Logging](/docs/concepts/provenance).
