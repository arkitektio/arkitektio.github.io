<Callout type="info" title="We don't want your data">

Arkitekt is a middleman, not a data silo. When you run your own hub, the data stays on
infrastructure you control and we never see it. The parts of the platform that do touch personal
data are kept to a minimum and described in the [Privacy Policy](/docs/privacy).

</Callout>

## The trust model in brief

- **Every request is authenticated and authorized.** See [Security Measures](#security-measures).
- **The organization is the hard boundary.** See
  [Organizations](/docs/concepts/terminology#the-hard-boundary).
- **Open by default within your organization**, with role-based access control on top. See
  [Open by default](/docs/concepts/terminology#open-by-default-within-your-organization).
- **You and the machine stay distinct.** See [You and the Machine](#you-and-the-machine).

The details are in [Identity & Access](/docs/concepts/security/identity) (how you and your apps log
in), [Data & Privacy](/docs/concepts/security/data-privacy) (where your data lives),
[The Mesh](/docs/concepts/security/mesh) (reaching a hub across networks) and
[Performance & Real-time](/docs/concepts/performance).

## Honest limits

<Callout type="warn" title="Arkitekt is early-stage software">

- We currently **discourage multi-user production deployments**; see [the production readiness of
  Arkitekt](/docs/concepts/deployment/planning).
- Remote features such as online monitoring and remote control are best run behind
  a **VPN** or the mesh for now. See [Using a VPN](/docs/concepts/security/mesh#arkitekt-through-a-vpn).
- **Scope-based access control is not yet fully enforced**; see
  [Scopes](/docs/concepts/security/identity#scopes).
- Data on the public **`demo.arkitekt.live`** instance is stored **unencrypted**, so treat it as
  public; see the [Privacy Policy](/docs/privacy#tier-4-demoarkitektlive).

</Callout>

## Security Measures [#security-measures]

Most scientists are good actors, but some data is sensitive, and scientific software has bugs. A
platform others build on has to make sure that a faulty plugin cannot delete your database.

**Everything is authenticated and authorized.** Every request to the API is made by a logged-in user
through an approved app, and is checked against their permissions. There is no anonymous access.

**Apps ask for permissions.** An app declares the scopes it needs, and you approve them when it first
connects. Scopes are meant to limit an app to the data it needs; enforcement is not complete yet (see
above).

**Plugins are sandboxed.** Plugins run in containers. They cannot reach the data of other plugins
or your file system, only the platform's protected APIs.

**TLS.** On your own hub you can enable TLS to encrypt traffic between apps and the hub. The ports a
hub exposes, including HTTPS, are listed in the [requirements](/docs/reference/requirements).

**Multi-tenancy.** One hub can host several **organizations**, each with its own users, data and
configuration, fully isolated from the others. Inside an organization, access is open by default and
can be narrowed with roles. See [Organizations](/docs/concepts/terminology#organization).

**Admin configuration.** Administrators can configure apps, plugins and the system remotely, down to
blocking a particular app for a day.

**Audit logs and restoration.** Newer services keep audit logs of what was done to the data, by whom
and through which app. Most changes can be reverted.

## You and the Machine [#you-and-the-machine]

Access control is half of the story. The other half is **provenance**: knowing who did what to which
data. Now that AI agents act inside our systems, Arkitekt keeps **you** and **the machine** distinct,
even when the machine acts on your behalf. Handing work to an app or an AI agent should never cost
you the ability to say later how a result was made. How the audit trail is recorded, attributed and
queried is described in [Provenance & Audit Logging](/docs/concepts/provenance).
