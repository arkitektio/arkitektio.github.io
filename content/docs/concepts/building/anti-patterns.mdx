None of these mistakes raises an error. They work in a demo and break once a second user, a
workflow or a restart turns up. Each breaks one of [the patterns behind Arkitekt](/docs/concepts/patterns).
The examples are Python, but the rules hold for every client, because they are about the
[shared model](/docs/concepts/building/shared-concepts). `Hardware` in the examples is the app's
device and model, kept in a context as [shown below](#handles).

| Anti-pattern | Do this instead |
|---|---|
| [Getter actions for state](#getters) | Publish it with `@app.state` |
| [UI that keeps its own copy of the app's state](#ui-state) | Bind the UI to the published state |
| [Large arrays in state](#large-arrays) | Store the data, publish a reference or a summary |
| [State as a real-time channel](#frequency) | Publish what is actionable at that rate, stream the rest |
| [Device handles and models in state](#handles) | `@app.context` |
| [Work at import time, module-level globals](#import-time) | Startup hooks and context |
| [A plain action that orchestrates](#orchestration) | `@app.workflow` with a protocol |
| [Large data inline in ports](#inline-data) | Structures, passed by reference |
| [Memory structures as the default](#memory-structures) | One action for steps that belong together, or a data service |

## Getter actions for state [#getters]

An action like `get_position()` that only reports what the app already knows turns every UI into a
poller. Each call is a task that is scheduled, routed, run and recorded. Ten panels polling twice a
second are twenty useless tasks a second, the value is unknown between polls, and a workflow cannot
[guard](/docs/guides/python/durable-execution#guard) on an action.

Publish the value as state instead. Assigning a field sends the change once, to everyone watching:

```python
@app.state
class Stage:
    x_um: float = 0.0
    y_um: float = 0.0
    moving: bool = False


@app.startup
def home() -> Stage:
    return Stage()


@app.action
def move_to(stage: Stage, hardware: Hardware, x_um: float, y_um: float) -> None:
    """Move To"""
    stage.moving = True
    hardware.driver.move(x_um, y_um)
    stage.x_um, stage.y_um = x_um, y_um   # published
    stage.moving = False
```

Actions are for things that do or compute something. If the answer is already in the app, it is
state.

## UI that keeps its own copy of the app's state [#ui-state]

A panel (or a Qt widget) that sets `acquiring = true` when its Start button is clicked has its own
opinion of the device. It is wrong when the call failed, when a workflow or a colleague stopped the
camera, after a restart, and in every other open panel.

Let the app own the truth. The UI shows the published state and calls actions:

```xml
<Blok kind="agent" context="panel">
  <Card>
    <Text>{self.Camera.acquiring ? "Acquiring" : "Idle"}</Text>
    <Button onClick={self.start() into starting}
            disabled={self.Camera.acquiring || starting.running}>Start</Button>
    <Button onClick={self.stop()} disabled={!self.Camera.acquiring}>Stop</Button>
  </Card>
</Blok>
```

`into starting` gives the panel the record of its own call, so it can show a request in flight
without claiming anything about the device.

**View state** is different: which tab is open, a slider value before Apply. It belongs to the viewer
and goes in a blok's `<local>`, not in `@app.state`. If two people looking at the app at once
should see the same value, it is app state.

## Large arrays in state [#large-arrays]

State is sent as a patch on every change, recorded in the agent's journal and held by the server. A
`numpy` array is refused when the app is assembled, so this mistake usually shows up as `.tolist()`:
a 2048 × 2048 frame as JSON is tens of megabytes, on every update, to every watcher.

Store large data in a data service and publish a **reference**, or a **summary** someone can act on:

```python
@app.state
class Acquisition:
    frames: int = 0
    saturated_pixels: int = 0                     # a summary someone can act on
    last_image: Image | None = None               # a reference: Mikro holds the pixels
```

Keep state to what you would write on a whiteboard next to the instrument: positions, flags,
counters, a barcode, a reference.

## State as a real-time channel [#frequency]

A background loop that writes a frame counter or a 1 kHz encoder value into state sends one update
per assignment. Each is sent to the server, journaled and fanned out to every watcher, with nothing
merged or dropped, in the same queue as the progress, logs and results of the app's tasks. A chatty
state slows down everything else, and because every update travels through the server, a live view
built on it stutters and a control loop reacts too late.

Two questions decide whether a value belongs in state, and how often to write it:

1. **Would a workflow guard on it, or a person decide on it?** `acquiring` or `exposure_ms`: yes. A
   per-frame counter: no.
2. **Is it actionable at the rate you push it?** Write a value when it changes meaningfully, not every
   time you read it.

Send live data through a channel built for it. For video and fast signals that is Lovekit (the
`lovekit` extra), which streams over WebRTC. State only says which streams exist:

```python
from lovekit import Lovekit, VideoStream, to_rgba
from lovekit.api.schema import Stream


@app.state
class Camera:
    exposure_ms: float = 10.0
    acquiring: bool = False
    saturated: bool = False                       # changes rarely, and a workflow can guard on it
    streams: list[Stream] | None = None           # where to watch, not what to watch


@app.background
async def live_view(camera: Camera, hardware: Hardware, lovekit: Lovekit) -> None:
    async with lovekit.publish([VideoStream("camera", title="Live view")]) as live:
        camera.streams = list(live.streams)       # published once
        while True:
            frame = await hardware.camera.asnap()
            await live.video("camera").send(to_rgba(frame))   # 50 fps, never touches state
            saturated = bool((frame == 65535).any())
            if saturated != camera.saturated:     # publish the change, not the reading
                camera.saturated = saturated
```

For a spectrum or trace, use a `DataStream`. When several fields change together, group them into one
update with `with task.updating(stage):`, so nobody sees the new x with the old y.

## Device handles and models in state [#handles]

State is published, so its fields must be serialized. A serial port or DLL handle cannot be, and 2 GB
of model weights should not be. Put private, process-bound objects in a **context**: shared by the
app's actions, built by a startup hook, never published.

```python
from dataclasses import dataclass


@app.context
@dataclass
class Hardware:
    driver: Driver
    model: Network


@app.startup
def open_hardware() -> Hardware:
    return Hardware(driver=Driver("/dev/ttyUSB0"), model=load("model.pt"))


@app.shutdown
def close_hardware(hardware: Hardware) -> None:
    hardware.driver.close()
```

Publish what the device is doing as state. Keep what the device is as context.

## Work at import time, module-level globals [#import-time]

Opening the device or loading the model at module level runs that work on every import. The CLI
imports your module to inspect, check and package it, and `arkitekt run dev` imports it on every
reload, on the build machine and in CI. A global is also invisible to the platform and hard to
replace in a test. Do the work in a startup hook and take the result by annotation, as in the
context example above.

## A plain action that orchestrates [#orchestration]

A plain action that calls other actions, or a script that drives a multi-step experiment in a loop,
leaves no record of which calls it made if it dies. Nobody can tell whether the dispense happened,
so nothing can be resumed. Arkitekt refuses this: a client call from inside a task raises
`RootOnlyCallError`, and a plain action that depends on an action demand is reported when the app is
assembled.

Declare what you need as a protocol and orchestrate in an `@app.workflow`. Its calls are recorded,
so a crashed workflow resumes where it was:

```python
@app.declare(app="liquid-handler", auto_resolvable=True, min=1)
class LiquidHandler(Protocol):
    def dispense(self, well: str, volume_ul: float) -> None:
        """Dispense"""
        ...


@app.workflow
def stain_and_measure(well: str, handler: LiquidHandler, *, task: Task) -> None:
    """Stain And Measure"""
    handler.dispense(well=well, volume_ul=0.5)
```

See [Workflows](/docs/guides/python/workflows) and [Durable execution](/docs/concepts/patterns/durability).

## Large data inline in ports [#inline-data]

Pixels, traces or tables passed as plain values (`list[list[float]]`) are serialized into the task,
stored with its history and sent through the server on every call. Orkestrator cannot offer "an
image" to pick, the workflow editor cannot check that the output fits the next step, and provenance
has no dataset to point at. Take and return a **structure** such as Mikro's `Volume`: the data stays
in its service and only a reference travels.

## Memory structures as the default [#memory-structures]

Registering `np.ndarray` as a [memory structure](/docs/guides/python/types#in-memory-structures) and
splitting a pipeline into small actions that hand arrays to each other looks clean, but it makes the
app stateful. Every returned array stays in the agent's memory until Rekuest tells it to collect that
reference or the agent stops. Run the pipeline on every acquisition and memory grows until the
process is killed. The references also work only on that one agent, and a restart breaks every
reference a running workflow still holds.

Keep steps that always run together in **one** action, calling plain functions:

```python
@app.action
def count_cells(path: str, sigma: float = 2.0) -> int:
    """Count Cells"""
    image = tifffile.imread(path)
    labels = segment(gaussian(image, sigma))      # plain functions, not actions
    return int(labels.max())
```

Store an intermediate result worth keeping in a data service. Memory structures fit an interactive
pipeline on one agent that a person rewires. See
[Arrays between actions](/docs/guides/python/examples/in-memory#use-it-sparingly).
