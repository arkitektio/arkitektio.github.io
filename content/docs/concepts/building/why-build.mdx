---
title: Why build on Arkitekt?
description: What Arkitekt gives a developer of bioimage analysis software, what it is not meant for, and where to start.
type: concept
---

Arkitekt lets you turn your analysis code into a tool that others can use and combine in live
workflows, without building the infrastructure around it yourself. It is modular, so you use only
the parts you need. What you get:

- **A UI and an API for free.** Declare a function as an action and Orkestrator shows it as a form.
  If you have a CLI tool, it gets a GUI. If you have a GUI, it gets a remote API.
- **Safe by default.** Every app is authenticated and acts for a user, so you can restrict who uses
  it and what it can reach. A development app cannot delete your data.
- **The rest of the ecosystem.** Your app can call actions of other apps, so a new algorithm does not
  need its own loader, viewer or segmentation step.
- **Workflows.** Every action you write can be used in a workflow without extra work.
- **Data from anywhere.** The same app runs on your laptop, a server or the cloud, and reads and
  stores data through the platform's services.

## What Arkitekt is not

- **Not a replacement for your analysis software.** Keep using and developing your specialised tools
  and GUIs. Arkitekt connects them to other apps and people.
- **Not a framework for massively parallel computing.** [Dask](https://dask.org/) and
  [Spark](https://spark.apache.org/) scale one analysis across many machines. Arkitekt connects and
  orchestrates many different tools in real time, and can call those frameworks from an app.

## Where to start

Decide which direction you are going:

- **[Build an app](/docs/guides/app-kinds)**: your code offers something others can call or watch,
  such as a packaged tool, a device, an app inside your own program or a workflow.
- **[Connect to the platform](/docs/guides/connect)**: your code only uses the platform, as a script,
  a notebook or a CI job.

Then pick a language. [Shared concepts](/docs/concepts/building/shared-concepts) explains the model
all of them follow.

- **Python**, the reference client: [Your first app](/docs/get-started/next-steps/first-python-app),
  then the [Python guides](/docs/guides/python).
- **Rust**, for fast agents and small binaries: [Your first Rust app](/docs/get-started/next-steps/first-rust-app).
- **Kotlin / Java**, an experimental client currently used only for the ImageJ plugin:
  [Kotlin / Java](/docs/guides/kotlin).
- **Embedded**, microcontrollers that offer actions themselves: [Your first device](/docs/get-started/next-steps/first-device).
- **Backend**, to write services of your own: [Backend libraries](/docs/concepts/services/backend-libraries).
