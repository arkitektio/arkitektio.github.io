[Understanding the basics](/docs/get-started/basics) introduces the three pieces: the hub, apps and
the coordinator. This page goes one level deeper: what each piece is made of, and what passes
between them when you run something.

## The Hub [#the-hub]

The hub is the part you install and the point every app connects to. It brokers work between apps
and stores what they produce, and it runs no analysis of its own. Why Arkitekt is built around a
middleman at all is the subject of
[Arkitekt the Middleman](/docs/concepts/philosophy#arkitekt-the-middleman).

A hub is not one program. It is a set of [services](/docs/concepts/services), each with its own
database and API, behind one gateway:

| Service | Job |
|---|---|
| [Rekuest](/docs/concepts/services/rekuest) | Knows the connected apps and their actions, and routes tasks to them |
| [Mikro](/docs/concepts/services/mikro) | Stores images and their metadata |
| [Fluss](/docs/concepts/services#fluss) | Stores and runs workflows |
| [Kabinet](/docs/concepts/services/kabinet) | The app store, from which apps are installed as containers |
| [Kraph](/docs/concepts/services/kraph) | The knowledge graph |

You choose which services a hub runs when you [plan a deployment](/docs/concepts/deployment/planning).
What that looks like on a machine is described in
[What you are setting up](/docs/concepts/deployment/what-you-are-setting-up).

<Callout type="info" title="Hub, server, deployment">

You will also see the hub called a **server** or a **deployment**. A server is a logical thing, not
necessarily one machine: a computer under your desk, a cluster, or a set of virtual machines in the
cloud.

</Callout>

## Apps [#apps]

Apps do the work. An app is any program that connects to a hub: Orkestrator, Fiji with its plugin,
napari, a Python script, a model in a container. Apps talk only to the hub, never to each other.

Orkestrator, the graphical interface, is not special. It is an app like any other, so you can use
Arkitekt entirely through its API, or build your own interface.

When an app connects, it declares its **actions**: what it can do, described by typed inputs and
outputs. For each action it offers an **implementation**, its own way of doing it, and several apps
can implement the same action. Each running copy of an app is an **agent**, and one app can run as
many agents on different machines. When you run an action, the hub creates a **task** and routes it to
an agent that has an implementation. You assign work to an action, never to a machine.

How these terms fit together, and how apps differ from services, is explained in [Terminology](/docs/concepts/terminology#how-do-these-elements-relate)
and [Apps vs Services](/docs/concepts/terminology#apps-vs-services).

## The Coordinator [#the-coordinator]

The coordinator is separate from the hub. It is the **control plane**: it knows who everyone is, and
it lets the pieces of a deployment find and trust each other. In Arkitekt this role is filled by
[Lok](/docs/concepts/services#lok). It has two jobs:

- **Authentication and authorization.** Users and apps sign in through OAuth2. Each app gets an
  identity of its own and only the permissions you approved, so the hub can record that a result was
  made by an app on your behalf. See [Identity & Access](/docs/concepts/security/identity).
- **Discovery.** An app finds a hub through the
  [Fakts protocol](/docs/concepts/services/service-discovery), a standard OAuth2 device flow whose
  token response also carries the configuration of each service the app asked for. Across networks,
  the coordinator hands out keys for the [mesh](/docs/concepts/security/mesh), so that app and hub can
  reach each other without opening ports.

The coordinator holds the accounts and never sees your data. The hub holds the data and keeps no
accounts of its own. Data moves between apps and the hub, the **data plane**, and the coordinator
only makes the introductions. Who runs the coordinator (us at go.arkitekt.live, your institute, or
you) is covered in
[Where Arkitekt runs](/docs/concepts/deployment/topology#three-ways-to-meet).

## One task, end to end

Here is what happens when you segment an image from Orkestrator:

1. **Log in.** Orkestrator gets a token and the hub's address from the coordinator. This happens
   once, not per task.
2. **Assign.** You pick the action and fill in its inputs. Orkestrator sends the request to Rekuest,
   which checks that you may call it and that the inputs match, and records the task.
3. **Route.** Rekuest chooses an implementation, and with it an agent, and sends the task there.
4. **Run.** The agent fetches the image from Mikro. Only a reference to it travelled with the task.
   The agent runs the segmentation and stores the mask in Mikro.
5. **Report.** Progress, logs and the reference to the mask stream back to Orkestrator. The task's
   history records who started it, which app ran it and in which organization, so the mask's
   [provenance](/docs/concepts/provenance) is known.

Nothing in this chain depends on where the agent runs, so you can move it to a GPU server, or swap
in another app that implements the same action, without changing how you call it.
