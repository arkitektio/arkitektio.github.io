<Callout type="info" title="The standard install">
  For a standard installation we advise the following path, and the rest of this page assumes it:

  1. **Create an account** on [go.arkitekt.live](https://go.arkitekt.live), our hosted coordination
     server. It stores only what a login needs, see the [privacy policy](/docs/privacy#tier-2-an-account-on-goarkitektlive).
  2. **Install Konstruktor** on the machine that will run the platform.
  3. In Konstruktor choose the **Hub** path and keep **go.arkitekt.live** as the coordination server.
  4. **Authorize** the hub in your browser with that account and press **Start**.

  Your data and compute stay on your machine. The account is only used so that you, your apps and
  your hub can find and trust each other. The command line, your own coordination server, raw
  docker-compose and Helm are all covered further down, but they are for advanced setups. If you
  want to understand *why* it is arranged this way, read [Where Arkitekt runs](/docs/design/philosophy/topology).
</Callout>

## What Konstruktor is [#konstruktor]

Konstruktor is the installer and admin tool for the Arkitekt platform. It is **one product with two
front ends**: a desktop app and a `konstruktor` command line tool. Both do exactly the same things,
authoring a hub, generating its Docker Compose project, authorizing it against a coordination server,
and driving Docker, because both are thin layers over the same core. They also share the same list
of known deployments, so a hub created in the app shows up in the CLI and the other way round.

Konstruktor creates two kinds of deployment:

- A **hub**: the data and compute services of Arkitekt, behind one gateway. This is what "installing
  Arkitekt" means, and what the rest of this page is about.
- A **plugin engine**: a single container that runs the plugins an organization installs, on this
  machine. See [Plugin engines](#plugin-engine).

Whatever it creates is an **ordinary Docker Compose project in a folder you choose**. There is no
Python, no helper container and nothing hidden: you can open the folder, read the compose file, and
run `docker compose` against it yourself if you ever want to.

## Requirements [#system-requirements]

**Docker, or a Docker-compatible engine, is the only dependency.** Konstruktor needs Docker Compose
**2.20** or newer and an Engine API of **1.41** or newer (Docker 20.10). Konstruktor checks this when it
starts and, if something is missing, tells you which of four things is wrong (no Docker binary, no
Compose, the daemon is not running, or the version is too old) and how to fix it. On the command line
`konstruktor doctor` prints the same advice.

| Operating system | Recommended engine | Also works |
|---|---|---|
| macOS | [Colima](https://github.com/abiosoft/colima): `brew install colima docker docker-compose` | OrbStack, Podman Desktop, Docker Desktop |
| Windows | [Rancher Desktop](https://rancherdesktop.io/): `winget install SUSE.RancherDesktop` | Podman Desktop, Docker Desktop |
| Linux | Docker Engine from your distribution | Podman with `podman-docker` and `podman-compose` |

On macOS and Windows the desktop app can install the recommended engine for you with one click. On
Linux the commands need `sudo`, so the app prints them for you to paste. If a machine has both Docker
and Podman, `KONSTRUKTOR_ENGINE=podman` picks Podman. You do **not** need a Docker account. Git is only
needed if you want to run a service from source.

**Hardware.** The platform is not yet optimized for low-end machines. We recommend at least **16 GB
of RAM**, a decent modern CPU, and **50 GB of free space on an SSD**. It runs on less (it works on a
Raspberry Pi 4), but transferring large amounts of data will be slow. As the hub moves a lot of data
between services and apps, a wired network connection helps a great deal, and on equal hardware the
platform runs noticeably faster on Linux than on Windows or macOS. GPUs are used by the **apps** that
do the heavy lifting, not by the hub, so the hub machine does not need one.

<Callout type="info" title="Where to install">
  The Arkitekt platform was designed as a multi-user platform that gets installed *once* on a **powerful** server and then
  can be accessed by multiple users and apps, on standard hardware. However it is also possible to install the platform on your own computer and
  use it as a `personal` platform. As long as not all safety features are implemented and audited, we recommend to use the platform
  in the latter way. We'll keep you posted, when we think the platform is safe ready for multi-user installations!
</Callout>

## Graphical installation (recommended) [#graphical-installer-recommended]

<Steps>
<Step>

### Download and install Konstruktor

Konstruktor is available for Windows, macOS (one universal build for Intel and Apple Silicon) and
Linux (`.deb`, `.rpm` and AppImage). Pick your platform and install it like any other desktop app.

<DownloadGrid />

</Step>
<Step>

### Let it check Docker

When Konstruktor opens it checks for a container engine. If Docker is ready you are through to the
home screen. If not, it tells you what is missing and offers to install the recommended engine
(macOS, Windows) or shows the commands to run (Linux). The check repeats until Docker is ready.

</Step>
<Step>

### Create a hub

Choose **New deployment** and then **Hub**. The wizard walks you through the following steps. For
the standard install you can accept the defaults everywhere except the folder and the identifier.

| Step | What you decide | Default |
|---|---|---|
| **Docker** | Nothing, this is the engine check again. | |
| **Folder** | Where the deployment lives, and its display name. The folder name seeds the identifier. | `~/MyHub` |
| **Coordination** | Which coordination server the hub trusts for accounts, and the hub's **identifier** (2 to 60 characters, letters, digits, `.`, `_`, `-`). Pick **go.arkitekt.live** (marked *Recommended*) or **Another server** for your institute's own. | go.arkitekt.live |
| **Services** | Which services the hub runs, and whether Rekuest runs here or on a remote host. Per service you can opt to run from source. | rekuest, mikro, fluss, kabinet, kraph |
| **Ports** | The HTTP and HTTPS ports the gateway publishes. Every service is routed behind them (`/rekuest`, `/mikro`, and so on). | 7080 / 7443 |
| **Storage** | Docker volumes (recommended) or the deployment folder for the database and uploaded files. | Docker volumes |
| **Addresses** | How far the hub is reachable (local only, this network, public) and which addresses it advertises to apps. At least one is required. | This network |
| **Mesh** | Whether the hub joins a mesh. See [Mesh](#mesh). | No mesh |
| **Review** | A summary of every choice and a preview of the files that will be written. | |

</Step>
<Step>

### Authorize the hub

A hub manages no accounts of its own. Users, organizations and permissions live on the coordination
server, and the hub has to be accepted there before it exists on disk. Konstruktor shows a short code
and a link. Open the link, sign in with your **go.arkitekt.live** account, pick the organization the
hub should belong to, and accept. Only when that grant comes back does Konstruktor write the
deployment. This is the same device-code flow apps use to connect, described in
[Service Discovery](/docs/design/architecture/service-discovery).

</Step>
<Step>

### Start it

The wizard writes the deployment and hands you over to the hub's **dashboard**. Press **Start**.
Docker pulls the images on first start, which takes a while depending on your connection. The
dashboard also lets you stop the hub, read logs, open the folder, edit the compose file, pull
updates, back up and restore data, and re-authorize.

The hub is seeded with an `admin` account whose password Konstruktor generated for you; **Copy
admin password** in the dashboard menu puts it on the clipboard. To create your own user, use the
**superuser** dialog on the dashboard once the hub is running, it creates the account in each
service.

Konstruktor also lives in the system tray, listing every hub and engine with its run state. Closing
the window does not stop anything.

</Step>
</Steps>

## Non-graphical installation [#cli]

Everything above can be done from a terminal with the `konstruktor` CLI, which is what you want on a
headless server, in a script, or in CI.

<Steps>
<Step>

### Install the CLI

<Tabs items={["Linux / macOS", "Windows"]}>
<Tab value="Linux / macOS">

```bash
curl -fsSL https://raw.githubusercontent.com/arkitektio/konstruktor/master/install.sh | sh
```

The script downloads the latest release for your architecture into `~/.local/bin`, verifies it
against the release's `SHA256SUMS`, and refuses to install if it cannot. With a terminal attached it
then asks for a hub identifier and creates a hub for you right away. Useful flags, passed after
`sh -s --`:

| Flag | Effect |
|---|---|
| `--no-run` | Install only, do not create a hub |
| `--hub-dir <path>` | Where to create the hub (default `~/MyHubs/<identifier>`) |
| `--version <tag>` | Install a specific release, for example `konstruktor-v0.4.1` |
| `--dir <path>` | Install the binary somewhere other than `~/.local/bin` |

`KONSTRUKTOR_INSTALL_DIR` and `KONSTRUKTOR_HUB_PARENT` do the same as `--dir` and `--hub-dir`.

</Tab>
<Tab value="Windows">

Download `konstruktor-x86_64-pc-windows-msvc.exe` from the
[releases page](https://github.com/arkitektio/konstruktor/releases/latest), rename it to
`konstruktor.exe` and put it somewhere on your `PATH`.

</Tab>
</Tabs>

</Step>
<Step>

### Create a hub

Interactively, the CLI asks the same questions as the wizard:

```bash
konstruktor hub create ~/MyHubs/lab-hub
```

Unattended, pass every answer as a flag. Without a terminal, a missing answer is an error naming
the flag that would have supplied it, so a script never hangs on a prompt:

```bash
konstruktor hub create ~/MyHubs/lab-hub \
  --server go.arkitekt.live \
  --identifier lab-hub \
  --services rekuest,mikro,fluss \
  --yes
```

The flags mirror the wizard steps: `--server`, `--identifier`, `--name`, `--services`,
`--rekuest local|<host>`, `--http-port`, `--https-port`, `--ssl`, `--storage volumes|folder`,
`--reach local-only|this-network|public`, `--host <addr>` (repeatable), `--mesh none|coordination|manual`,
`--dev`, `--no-start`, `--no-open`. Run `konstruktor hub create --help` for the full list.

The one step that stays interactive is the **authorization**: the CLI prints the link and the code,
and someone with an account accepts the hub in a browser. If that fails the command exits with
code `4`. On success the hub's path is printed on standard output and, unless you passed
`--no-start`, the hub is started.

</Step>
<Step>

### Run it

```bash
konstruktor status lab-hub      # what is running
konstruktor up lab-hub          # start
konstruktor stop lab-hub        # stop
konstruktor logs lab-hub --service mikro --tail 200
konstruktor superuser mikro --in lab-hub   # create a user in a service
konstruktor backup ./backup --in lab-hub
konstruktor restore ./backup --in lab-hub
konstruktor list                # every hub and engine this machine knows
```

A target can be a path or the name of a registered deployment, and defaults to the current
directory.

</Step>
</Steps>

Inside the deployment folder you will find `hub_config.yaml` (the hub profile: coordination server,
services, ports, image tags), the generated `docker-compose.yaml`, a `configs/` folder with one file
per service plus the gateway's `Caddyfile`, and `hub_credentials.json` holding the secrets. Edit the
compose file if you need to; Konstruktor keeps a `.bak` on every save.

## Plugin engines [#plugin-engine]

A **plugin engine** is the second thing Konstruktor can create: one container that runs the plugins
an organization has installed, on the machine where the engine lives. It is how a lab adds compute
to a hub without touching the hub itself. Choose **Plugin engine** in the app, or run:

```bash
konstruktor engine create ~/MyEngines/gpu-box --server go.arkitekt.live --identifier gpu-box
```

Engines are authorized against the coordination server the same way hubs are.

## Updating [#updating]

Arkitekt is a rapidly evolving platform, and updating regularly is the only way to get fixes and new
features. Two things update separately:

- **The platform images.** The dashboard checks the registries for newer images and shows, per
  service, whether the running image is current, whether a newer one exists, or whether a newer one
  has been pulled but is not running yet. **Pull images** and then **Start** applies an update; on
  the command line that is `konstruktor pull lab-hub` followed by `konstruktor up lab-hub`. Updates
  within a channel are meant to be backwards compatible and to keep your data intact.
- **Konstruktor itself.** There is no auto-updater. Re-run the install script, which always resolves
  the latest release, or download the new desktop installer.

<Callout type="info" title="About channels">
  Konstruktor no longer has a channel picker. A hub's channel is simply the set of image tags in its
  `hub_config.yaml`; a stock hub ships on the `next` tag (with Kraph on `dev`). To move a service to
  another channel, change its tag there and pull. How the channels relate is described in
  [How we version Arkitekt](/docs/design/philosophy/version).
</Callout>

## Mesh [#mesh]

The **Mesh** step of the wizard (or `--mesh` on the command line) decides whether the hub can be
reached across networks through the [Arkitekt mesh](/docs/design/philosophy/topology#arkitekt-mesh):

- **No mesh** (`none`): the hub stays on the addresses you picked.
- **Join the organization's mesh** (`coordination`): Konstruktor asks the coordination server for a
  mesh key while it authorizes the hub, and runs a mesh sidecar next to the gateway.
- **Use a key I already have** (`manual`): paste a pre-authorized key and the control server URL,
  for a coordinator you run yourself (`--mesh-key`, or better `KONSTRUKTOR_MESH_KEY`, and `--mesh-coord-url`).

Joining is not the same as being advertised. Once the hub is up and has its mesh address, add that
address on the dashboard's address list and **Authorize** again, so apps arriving over the mesh are
told where to find the hub. What the mesh does and why it is the secure default is explained in
[The Mesh](/docs/design/security/mesh).

## Local-network advertising (removed) [#advertising]

<Callout type="warn" title="This feature was removed">
  Earlier versions of Arkitekt could **advertise** the platform on your local network with a UDP
  broadcast so that apps could discover it without knowing its IP address. Local networks turned out
  to be too much of a mess (firewalls, changing addresses, blocked broadcasts, VPNs) for that to be
  reliable, and it only ever worked within a single LAN. Apps now discover a hub by the addresses it
  advertises, and across networks through the [mesh](/docs/design/philosophy/topology#arkitekt-mesh).
</Callout>

## Other installation strategies [#other-installation-strategies]

These are not recommended for beginners, but are useful if you want to integrate the platform into a
larger infrastructure or take part in its development.

### Edit what Konstruktor generated [#custom-compose]

Because a hub is a plain Docker Compose project, the simplest customization is to let Konstruktor
generate it and then edit `docker-compose.yaml` and the files in `configs/` yourself, from the
dashboard's **Edit compose file** or with any editor. Konstruktor keeps a backup of the previous
version on each save.

### Docker-Compose [#docker-compose]

If you prefer to start from a maintained compose configuration rather than a generated one, we keep
one at [arkitektio/arkitekt-server](https://github.com/arkitektio/arkitekt-server). It includes the
most common services and, when cloned with `git clone --recurse-submodules`, their source code. If you
run into problems with it, please open an issue in that repository.

### Helm Charts [#helm-charts]

We are working on a Helm chart for installing Arkitekt on a Kubernetes cluster; it will live at
[arkitektio/arkitekt-helm](https://github.com/arkitektio/arkitekt-helm). Until then the compose
configuration can be converted with [kompose](https://kompose.io/).

### Custom installation [#custom-installation]

From here be dragons. You can find hints in the developer section of each service and in each
service's own documentation. At this point you are on your own. If you encounter problems, please
open an issue in the respective repository.
