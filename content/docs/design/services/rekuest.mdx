## Rekuest Design

Rekuest is two programs that are released together and always run as a pair:

- **The Rekuest server** (Python) is what clients and the UI talk to. It serves the GraphQL API and
  its subscriptions, holds the catalogue of actions and implementations, and owns the database
  schema.
- **takt** (Rust) is the backend for task assignment. It holds every agent's connection, registers
  what an agent declares, assigns tasks, delivers controls such as cancel, interrupt and pause, and
  runs every deadline: lost agents, redelivery, schedules, triggers and retention.

Both read the same configuration file and share one Postgres database and one Redis. Neither keeps
state of its own, so each can run as several replicas.

```
agents ──── websocket ─────┐
webhook agents ── HTTP ────┤
hub services ── signals ───┤
                           ▼
                 takt (Rust, N replicas) ◀── internal API ── Rekuest server (Python, GraphQL)
                           │                                          │
                           └─────────── Postgres · Redis ─────────────┘
```

A gateway in front of the pair sends the agent routes to takt and everything else to the server.
When a GraphQL mutation needs something done to a task or an agent, the server asks takt over a
signed internal API; takt is the only writer of task state.

<Callout type="info">

Earlier versions of Rekuest queued tasks through a message broker (RabbitMQ). That is gone: tasks
are rows in Postgres, and Redis carries the queues to connected agents and the events between
replicas.

</Callout>

### Why task assignment is written in Rust

An agent's reports and its heartbeat answers must not wait behind API work. When GraphQL, every
agent connection and every subscription lived in one Python process, they did: under load from the
UI, agents fell behind on their heartbeat and were disconnected. Moving the agent side into its own
program removed that coupling. Measured with one agent streaming a report every 50 ms while two
workers query GraphQL:

| GraphQL load | Agent protocol inside the Python server | takt |
|---|---|---|
| none | 19.5 reports/s, acknowledged after 0.22 s | 19.9 reports/s, 0.14 s |
| 10 queries/s × 2 | 9.2 reports/s, 5.3 s, agent disconnected | 19.4 reports/s, 0.13 s |
| 26 queries/s × 2 | agent already gone | 19.2 reports/s, 0.12 s |

What this means for throughput and real-time behaviour is discussed in
[Performance & Real-time](/docs/design/security/performance).

### What happens when a task is assigned

1. The caller names an action, or one implementation of it, and passes arguments. takt checks the
   arguments against the action's ports.
2. takt resolves the implementation's **dependencies**: the other apps it calls while it runs. A
   dependency may have dependencies of its own, so the whole tree is resolved at once and frozen
   onto the task. Every call the task later makes reaches the agents chosen at this moment.
3. The task is stored, and handed to the agent as soon as the row is committed. A task whose agent
   is offline waits for it.
4. The agent reports what it does. Each report is stored once and acknowledged, and the caller sees
   it as it arrives.

### Challenges as a Distributed System

Rekuest is the backbone of distributed task execution in Arkitekt, so it has to behave well when the
things it connects fail. Its contract for that is specific:

- **Reports are not lost.** Every agent journals what it reports to disk and resends everything the
  server has not acknowledged, after a reconnect and after a restart.
- **Nothing is re-run on guesswork.** Work that no agent picked up is delivered again. Work whose agent
  died while running it ends **LOST**, meaning "outcome unknown", and the caller decides.
- **Workflows survive their agent.** A workflow task is resumed from its journal, and the calls it
  already made return their recorded results instead of running again.

[Durable execution](/docs/design/architecture/durable-execution) describes this in full.

Every deadline behind that contract is a column in the database, and takt's replicas sweep them. One
replica sweeps per tick and every transition has exactly one winner, so a replica can stop at any
moment without a deadline being missed.
