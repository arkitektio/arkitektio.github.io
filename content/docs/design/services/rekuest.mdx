## Rekuest Design

Rekuest itself is designed as a stateless service (in order to be able to scale horizontally), and
interfaces with proven open-source technologies, such as [Redis](https://redis.io/) and [RabbitMQ](https://www.rabbitmq.com/).
to route tasks to the appropriate apps. The following diagram shows the high-level design of Rekuest:

### Challenges as a Distributed System

Rekuest is the backbone of distributed task execution in Arkitekt, so it has to behave well when the
things it connects fail. Its contract for that is specific:

- **Reports are not lost.** Every agent journals what it reports to disk and resends everything the
  server has not acknowledged, after a reconnect and after a restart.
- **Nothing is re-run on guesswork.** Work that no agent picked up is delivered again. Work whose agent
  died while running it ends **LOST**, meaning "outcome unknown", and the caller decides.
- **Workflows survive their agent.** A workflow task is resumed from its journal, and the calls it
  already made return their recorded results instead of running again.

[Durable execution](/docs/design/architecture/durable-execution) describes this in full. Rekuest
itself is a comparatively thin layer over proven infrastructure. A message broker (RabbitMQ) queues
and distributes tasks, and a websocket API wraps it to authenticate agents and callers, authorize
calls, and track the health of every connected app. What this means for throughput and real-time
behaviour is discussed in [Performance & Real-time](/docs/design/security/performance).
