Lab work runs for hours on machines that crash and lose power. The `recovery/` folder has three apps
that work together, and a few smaller examples. They show what Arkitekt does when the process
running a task dies, and what your code decides. This page walks through the code. The rules
themselves are in the [Durable execution](/docs/guides/python/durable-execution) guide.

<Prerequisites>

- [Actions on stored data](/docs/guides/python/examples/stored-data) (the analysis app works on Mikro images)
- [A device with live state](/docs/guides/python/examples/device-state)

</Prerequisites>

<Learn>

- Say what running an action again would do, with `effects=`
- Write a workflow that calls other apps' actions with `@app.declare` and `@app.workflow`
- Handle a step whose agent died: `AgentLost`, `task.retry`, `task.hold`
- Notice that the world changed while a workflow was down, with `task.guard`
- Keep state across a restart with `@app.state(persist=...)`

</Learn>

## The setup

| App | File | Role |
|---|---|---|
| `segmentation` | `declare_analysis.py` | counts and segments cells in an image from Mikro |
| `liquid-handler` | `declare_robot.py` | a robot that dispenses into the wells of a plate |
| `plate-workflow` | `workflow.py` | counts the cells in a well's image, doses dye in proportion, reads the well |

The rule to remember: **the server never re-runs a task on its own.** The one exception is a task
that no agent ever picked up. Every other decision is made in code, by whoever called the task.

## Saying what a repeat would do: `effects=`

Whoever has to decide about a lost task needs to know one thing first: what happens if it runs
again? The apps answer that with `effects=`. The scale goes from harmless to dangerous:

| `Effects` | Running it again… | Example here |
|---|---|---|
| `NONE` | changes nothing | `count_cells`, `read_absorbance` |
| `REPEATABLE` | leaves the same result as once | (`set_flow` on the previous page) |
| `UNKNOWN` (the default) | nobody has said | `segment`, which stores a new dataset |
| `IRREVERSIBLE` | happens again in the real world | `dispense` |

The analysis app:

```python title="recovery/declare_analysis.py"
@app.action(effects=Effects.NONE)
def count_cells(image: Annotated[SingleChannelImage, Description("The image to count in")]) -> int:
    """Reads the image and counts the objects in it. Changes nothing, so if its agent
    dies, it is simply run again (AT_LEAST_ONCE) unless the caller says otherwise.
    """
    pixels = np.asarray(image.data)
    return int(label(pixels > threshold_otsu(pixels)).max())


@app.action
def segment(
    mikro: Mikro,
    image: Annotated[SingleChannelImage, Description("The image to segment")],
) -> LabelMask:
    """Stores a new label dataset next to the image. No claim (UNKNOWN), and honestly
    so: a re-run stores a *second* dataset. By default a lost run fails; a caller
    who'd rather clean up a duplicate than lose the run asks for AT_LEAST_ONCE.
    """
    pixels = np.asarray(image.data)
    labels = xr.DataArray(
        label(pixels > threshold_otsu(pixels)).astype(np.uint16), dims=image.data.dims
    )
    result = mikro.create_array_dataset(
        data=labels,
        scales=[],
        name="labels",
        axes=image.carried_axes(labels.dims),
        derived_from=[image.derive_identity(value_relation="TRANSFORMED")],
    )
    return result.lens()
```

`count_cells` only reads, so it claims `NONE`. `segment` makes no claim, and that is honest: running
it twice stores a second label dataset. (The docstrings mention `AT_LEAST_ONCE`, an older way of
describing a retry. In the current version nothing is re-run unless the caller's code does it, as
below.) The robot sets a default for the whole app instead:

```python title="recovery/declare_robot.py"
app = App("liquid-handler", "0.1.0", effects=Effects.IRREVERSIBLE)


@app.state(name="plate")  # the key a workflow's `plate:` demand asks for
class Plate:
    """The plate on the deck, and what has gone into it."""

    barcode: str = ""
    dispensed_ul: dict[str, float] = field(default_factory=dict)


@app.startup
def no_plate() -> Plate:
    """Start with an empty deck."""
    return Plate()


@app.action
def load_plate(plate: Plate, barcode: str) -> str:
    """Records a new plate on the deck. Any guard on the old plate now fails.
    """
    plate.barcode = barcode
    plate.dispensed_ul = {}
    return barcode


@app.action
def dispense(plate: Plate, well: str, volume_ul: float, *, task: Task) -> float:
    """Moves liquid into a well. Running it again puts twice the volume in the well.
    """
    for step in range(10):
        task.progress((step + 1) * 10, f"Dispensing into {well}")
        koil.sleep(0.2)
    plate.dispensed_ul = {**plate.dispensed_ul, well: plate.dispensed_ul.get(well, 0) + volume_ul}
    return volume_ul


@app.action(effects=Effects.NONE)
def read_absorbance(well: str) -> float:
    """Reads the plate reader. Moves nothing, so it overrides the app's default.
    """
    return 0.42
```

`App(..., effects=Effects.IRREVERSIBLE)` makes every action irreversible unless it says otherwise.
`read_absorbance` says otherwise. For a hardware app this is the safe default: an action that
forgets to make a claim is treated as dangerous, not as harmless.

The robot also publishes its `plate` as state: the barcode of the plate on the deck and what went
into which well. The workflow uses that below.

<Callout type="info" title="Information, not a rule">

`effects=` never makes the server do anything. It is shown to whoever decides: the workflow reads it
from the exception, and a person sees it in Orkestrator.

</Callout>

## The workflow

### Declaring what it needs

```python title="recovery/workflow.py"
class PlateState(Protocol):
    """What the workflow reads of the robot's plate: the fields its ``plate`` state must have."""

    barcode: str
    dispensed_ul: dict[str, float]


@app.declare(app="segmentation", auto_resolvable=True, min=1)
class Segmentation(Protocol):
    """What this workflow needs from the segmentation app."""

    def count_cells(self, image: SingleChannelImage) -> int:
        """Count Cells"""
        ...

    def segment(self, image: SingleChannelImage) -> LabelMask:
        """Segment"""
        ...


@app.declare(app="liquid-handler", auto_resolvable=True, min=1)
class LiquidHandler(Protocol):
    """What this workflow needs from the liquid handler."""

    plate: PlateState

    def dispense(self, well: str, volume_ul: float) -> float:
        """Dispense"""
        ...

    def read_absorbance(self, well: str) -> float:
        """Read Absorbance"""
        ...
```

A workflow doesn't import the other apps. It describes the actions and state it needs as a
`Protocol`, and `@app.declare(app=...)` turns that into a dependency. When the workflow runs, the
platform finds a running `segmentation` agent and a running `liquid-handler` agent that match.
`plate: PlateState` asks for the robot's `plate` state, with these fields.

### Counting and segmenting

```python title="recovery/workflow.py"
@app.workflow
def stain_and_measure(
    segmentation: Segmentation,
    handler: LiquidHandler,
    image: SingleChannelImage,
    well: str,
    *,
    task: Task,
) -> float:
    """Counts the cells in the well's image, doses dye in proportion, then reads the well.
    """
    started = task.now()  # recorded: a resumed run sees the same start time

    # count_cells changes nothing: if its agent dies, just try again, even after it
    # started. task.retry retries only on AgentLost, and only a started step when told.
    cells = task.retry(segmentation.count_cells, image, attempts=3, if_started=True)

    # segment stores a dataset and makes no claim. If its agent dies after it
    # started, a retry might leave a duplicate. This workflow keeps the labels only
    # for the record, so it goes on without them rather than guess.
    try:
        segmentation.segment(image)
    except AgentLost as lost:
        task.log(f"segmentation lost ({lost.last_progress}%), continuing without labels")
```

`@app.workflow` marks an action that is allowed to call other actions. A plain `@app.action` may
not. Two things are different about a workflow:

- **If its own agent dies, the platform resumes it.** The code runs again from the top, but every
  call that already finished returns its recorded result instead of running again. `count_cells` and
  `segment` are not repeated.
- **In return, the code must be deterministic.** Values from outside come in only through calls and
  `task`. That's why the start time is `task.now()` (recorded, so a resumed run sees the same value)
  and not `time.time()`.

If a **step's** agent dies, the call raises `AgentLost`, and the workflow decides. Here it decides
in two ways:

- `count_cells` changes nothing, so `task.retry(..., if_started=True)` runs it again, up to three
  times, even if it had already started.
- `segment` might leave a duplicate dataset if repeated, and the labels are only kept for the
  record. So the workflow logs the loss and goes on without them.

### Dispensing

```python title="recovery/workflow.py"
    volume = 0.5 * cells
    try:
        with task.guard(handler.plate, "barcode"):
            try:
                handler.dispense(well, volume_ul=volume)
            except AgentLost as lost:
                if not lost.started:
                    # Never reached the robot: nothing was dispensed.
                    handler.dispense(well, volume_ul=volume)
                else:
                    # Started, irreversible, fate unknown. A person checks the well,
                    # then approves (the dispense counts as done) or denies (abandon).
                    decision = task.hold(
                        f"Dispense of {volume} µl into {well} was lost: "
                        "check the well, then approve to go on or deny to abandon.",
                        lost=lost,  # its effects and last progress, in front of the person
                    )
                    if not decision.approved:
                        raise RuntimeError(f"Abandoned at {well}: {decision.answer or 'denied'}")
            absorbance = task.retry(handler.read_absorbance, well, attempts=3, if_started=True)
    except StateChanged as changed:
        # The plate was swapped while this workflow was down: whatever comes next
        # would land in the wrong plate.
        raise RuntimeError(f"Not continuing: {changed}") from None

    task.log(f"{cells} cells, {absorbance:.3f} OD, {task.now() - started:.1f}s")
    return absorbance
```

The dispense is where a wrong decision costs something real. `AgentLost` carries what is known:

- `lost.started` is `False`: the robot never picked the task up. Nothing was dispensed, so sending
  it again is safe.
- `lost.started` is `True`: the robot started and then died. Some liquid may be in the well. The
  workflow can't know, so it **asks a person**. `task.hold(...)` pauses the workflow and shows the
  message, together with the lost step's effects and last progress. The person checks the well and
  approves (go on, the dispense counts as done) or denies (abandon).

`with task.guard(handler.plate, "barcode"):` protects the block against a changed world. It records
the revision of the robot's `plate` state. If the workflow's agent dies and the workflow is resumed
later, the guard checks whether the barcode was changed by something other than this workflow, for
example because someone loaded a different plate in the meantime. If so, it raises `StateChanged`
instead of dispensing into the wrong plate.

## Keeping state across a restart

The robot forgets its plate when it restarts. `persisted_state.py` shows how an app remembers:

```python title="recovery/persisted_state.py"
"""Read what an earlier run knew, after a restart or a power cut.

``@app.state(persist=...)`` keeps the state's last value on disk, and a startup hook of
the next run takes it as ``old: Stage | None``. Asking for a state without ``persist`` is
refused when the app is declared.

- ``persist=1.0`` writes at most once a second, off the event loop. A power cut loses
  about that much.
- ``persist="synchronous"`` writes every change and fsyncs it on the event loop. Nothing
  is lost, so keep it for states that change rarely.

``old`` is what the agent last knew, not what the hardware did: here the stage may have
moved after that last write, so the hook reads the real position and compares. It is
``None`` on a first run, after a version bump, or when the state's fields changed.
"""

from arkitekt import App, run

app = App("stage", "0.1.0")


@app.state(name="stage", persist=1.0)
class Stage:
    """Where the stage is, and whether it stopped where it was last known to be."""

    position_um: float = 0.0
    moved_while_down: bool = False


def read_encoder() -> float:
    """Reads the stage's real position."""
    return 12.5


@app.startup
def start(old: Stage | None) -> Stage:
    position_um = read_encoder()
    moved = old is not None and abs(old.position_um - position_um) > 0.1
    return Stage(position_um=position_um, moved_while_down=moved)


if __name__ == "__main__":
    run(app)
```

`persist=1.0` writes the state to disk at most once a second. On the next start, a startup hook that
asks for `old: Stage | None` gets the last saved value, or `None` on the first run. The hook doesn't
trust it blindly: `old` is what the agent last *knew*, so it reads the encoder and compares. If the
stage moved while the app was down, `moved_while_down` says so.

## From a script

A script that calls actions directly is the caller, so a lost task is its decision too.
`call_directly.py` does the same as the workflow, but with `connect` and the top-level `retry`:

```python title="recovery/call_directly.py"
from mikro import Mikro
from rekuest.client.client import RekuestCaller

from arkitekt import AgentLost, connect, retry

COUNT = "segmentation/count_cells"
DISPENSE = "liquid-handler/dispense"

IMAGE_DATASET = "1234"  # an image already in mikro


def main() -> None:
    """Count the cells, then dose: retry the one, ask a person about the other."""
    with connect(RekuestCaller, Mikro, identifier="plate-runner") as (rekuest, mikro):
        image = mikro.get_array_dataset(IMAGE_DATASET).lens()

        # Counting changes nothing: if its agent dies, try again, even after it started.
        cells = retry(rekuest.call, COUNT, image=image, attempts=3, if_started=True)

        try:
            rekuest.call(DISPENSE, well="A1", volume_ul=0.5 * cells)
        except AgentLost as lost:
            if not lost.started:
                # It never reached the robot: nothing was dispensed, sending it again is safe.
                rekuest.call(DISPENSE, well="A1", volume_ul=0.5 * cells)
            else:
                # Started, and running it again would happen again in the real world.
                print(
                    f"The dispense into A1 was lost at {lost.last_progress}% "
                    f"(effects: {lost.effects}). Check the well before doing anything else."
                )
```

`RekuestCaller` is the client that starts tasks. A script is not resumed if it dies, so
orchestration that must survive a crash belongs in a workflow.

## Try it

Start the three apps in three terminals:

```bash
uv run --script examples/recovery/declare_analysis.py
uv run --script examples/recovery/declare_robot.py
uv run --script examples/recovery/workflow.py
```

The workflow takes a `SingleChannelImage`: two spatial axes and at most one channel. None of the
uploads so far is one. The easiest way to get one is to run `read_with_bioio.py` on a single-plane,
single-channel TIFF of your own. It drops the padded axes and uploads a plain `y, x` image.

Load a plate (**Load Plate** with any barcode), then run **Stain And Measure** on that image. While
it dispenses, kill the robot's process with `kill -9`. Once the grace window has passed, the
dispense should come back as `AgentLost` with `started` set, so the workflow holds, and Orkestrator
shows you its message with the dispense's effects and last progress. Restart the robot and approve
the hold. The workflow should then go on to the absorbance reading.

The [failure scenarios](https://github.com/arkitektio/arkitekt/blob/main/examples/recovery/README.md#failure-scenarios)
in the folder's README list more things to try.
