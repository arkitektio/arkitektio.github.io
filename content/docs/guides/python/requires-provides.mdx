A port's type says what **class** of object it takes. For most structures that is not enough.

Every array in [Mikro](/docs/concepts/services/mikro) is seen through the same class, an
`ArrayLens`. A 2D plane, a z-stack, a timelapse, a two-colour volume: all `ArrayLens`. Whether a
given lens is a volume is not something its class knows. It is a feature of **that instance**: how
many of its axes are spatial, how many channels it has, how large it is. A deconvolution that needs
a z-stack cannot say so with a class.

**`Requires` and `Provides` narrow a port by such instance features.** They are constraints on the
object's **descriptors**: facts the service computes about each object and sends along with it.

## Mikro's specs are constraints, not classes

`Volume`, `Image`, `SingleChannelImage` and the other specs in `mikro.arkitekt.specs` are not
subclasses. Each is `ArrayLens` with constraints attached:

```python
Volume = Annotated[
    ArrayLens,
    Requires(key="@mikro/n_space_axes", operator=DescriptorOperator.EQUALS, value=3),
    Provides(key="@mikro/n_space_axes", operator=DescriptorOperator.EQUALS, value=3),
]
```

So every one of these ports has the same structure identifier, `@mikro/arraylens`, and the same
Python class at run time. What differs is the constraint:

| Spec | Narrows `ArrayLens` to | Descriptor |
|---|---|---|
| `Image` | exactly two spatial axes | `@mikro/n_space_axes` = 2 |
| `Volume` | exactly three spatial axes | `@mikro/n_space_axes` = 3 |
| `Timeseries` | at least one time axis | `@mikro/n_time_axes` ≥ 1 |
| `SingleChannel` | at most one channel | `@mikro/n_channels` ≤ 1 |
| `SingleChannelImage` | a plane with at most one channel | both of the above |
| `MultichannelVolume` | a stack with a channel axis | `n_space_axes` = 3, `n_channel_axes` ≥ 1 |
| `LabelMask` | values that are object ids, not intensities | `@mikro/value_kind` = `categorical` |

The descriptor keys are constants in the same module (`N_SPACE_AXES`, `N_CHANNELS`, `N_TIMEPOINTS`,
`SIZE`, `DTYPE`, `EXTENSION`, …), and every one of them is a feature of the instance: two lenses of
the same class, even of the same dataset, can have different values.

## Which side does what

A spec carries both markers, and a port keeps the side that applies to it:

| Where | Keeps | Means |
|---|---|---|
| An argument | `Requires` | What the action **accepts**. Orkestrator's pickers offer only objects that fit. |
| A return | `Provides` | What the action **promises** to produce. |

```python
@app.action
def deconvolve(image: Volume) -> Volume: ...
```

`image` requires three spatial axes; the return provides three. Because both sides are written
down, a step's promise can be compared with the next step's demand: the output of `deconvolve` fits
anywhere a `Volume` is required.

Both are part of the **action**, the contract callers rely on, and `arkitekt inspect` shows them:

```json
{"key": "image", "identifier": "@mikro/arraylens",
 "requires": [{"key": "@mikro/n_space_axes", "operator": "EQUALS", "value": 3}]}
```

## How they are checked

- **Before the call.** Pickers in Orkestrator filter by the server's descriptors, so a person can
  only choose objects that fit.
- **On every call.** The run tests each object crossing a constrained port against its own
  descriptors, the ones the server sent with it. An argument that does not fit, or a return that
  breaks a promise, fails the task, saying which constraint it broke.
- **Provenance is promised, not measured.** Some descriptors cannot be read off the data. Whether a
  lens holds labels or intensities (`@mikro/value_kind`, which `LabelMask` narrows) is recorded from
  how the data was derived. It is never tested on the lens: an action that returns a `LabelMask`
  says it made labels, and only actions that take one are offered it.
- **Only what is there.** Descriptors arrive with the object, so checking costs no extra request.
  An object that was not fetched with its descriptors (one built by hand) has none, and a
  constraint on a key that is absent is not tested.

## Writing your own

A narrower spec is a plain assignment. An action that unmixes exactly two channels:

```python
from typing import Annotated

from arkitekt import DescriptorOperator, Provides, Requires
from mikro.api.schema import ArrayLens
from mikro.arkitekt.specs import N_CHANNELS, N_SPACE_AXES

DualColorVolume = Annotated[
    ArrayLens,
    Requires(key=N_SPACE_AXES, operator=DescriptorOperator.EQUALS, value=3),
    Provides(key=N_SPACE_AXES, operator=DescriptorOperator.EQUALS, value=3),
    Requires(key=N_CHANNELS, operator=DescriptorOperator.EQUALS, value=2),
    Provides(key=N_CHANNELS, operator=DescriptorOperator.EQUALS, value=2),
]
```

Files work the same way. An importer that only reads ND2 files narrows Mikro's `File` by its
extension:

```python
from mikro.api.schema import File
from mikro.arkitekt.specs import EXTENSION

Nd2File = Annotated[File, Requires(key=EXTENSION, operator=DescriptorOperator.IN, value=["nd2"])]


@app.action
def import_nd2(file: Nd2File) -> Volume:
    """Import ND2"""
    ...
```

The operators are `EQUALS`, `NOT_EQUALS`, `LTE`, `GTE`, `IN`, `NOT_IN`, `CONTAINS`, `MATCHES` and
`EXISTS`.

Three things to know:

- **Use a plain assignment**, never a PEP 695 `type DualColorVolume = ...` statement. That wraps
  the `Annotated` so the markers are silently dropped.
- **Specs carry no description.** A port takes one `Description`, so add yours where you use it:
  `Annotated[Volume, Description("The stack to deconvolve")]`.
- **"One channel" is an extent, not a missing axis.** `SingleChannel` means `n_channels <= 1`: a
  lens can pin one channel of a multichannel dataset, but it keeps the channel axis. Your code must
  tolerate a channel axis of length one.

## When to use them, and when not

Use `Requires` and `Provides` for features that **vary between instances of one class** and that
your code depends on: the number of spatial axes, channels or timepoints, a file format, a dtype.

Don't use them for what the class already says. If two kinds of object are genuinely different
(a file and an array, a table and an image), they are different structures with their own
identifiers, and the type alone keeps them apart. And don't use them for what one *machine* can
handle; that is `Fits`.

## `Fits`: what one deployment can handle

`Requires` is about the action: every implementation accepts the same objects. Some limits belong to
one machine instead. A volume of 40 GB is a valid `Volume`, but this agent has 16 GB of memory.
`Fits` says so, as a formula over the object's descriptors and the agent's hardware:

```python
@app.action
def denoise(
    volume: Annotated[Volume, Fits("@mikro/size * @mikro/dsize < agent.memory_mib * 1048576")],
) -> Volume: ...
```

A `Fits` lives on the **implementation**, not on the action, and is not part of its contract. The
formula is parsed, never run as code. An action is not offered for an object that no running
implementation fits, and an agent refuses one that reaches it anyway, so a larger machine running
the same app can take what this one cannot.

## In other languages

The Kotlin client declares `@Requires` and `@Provides` on structures and tests them the same way.
The constraints travel in the action's declaration, so they mean the same whichever language
declared them.
