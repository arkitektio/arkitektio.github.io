Sometimes the program already exists and is not going anywhere: microscope control software, a
napari plugin, a Qt GUI you wrote for an instrument, a service with its own main loop, or Fiji. It
owns the process, the event loop and the window. You want it to **also** be callable: offer a few
of its operations as actions and publish what it is doing.

Then the app lives **inside** that program. The program decides when Arkitekt starts and stops,
and the app is a guest in its process.

## Use it when

- Another program owns the **process and the event loop**, and should keep doing so.
- The actions need the program's **live objects**: its open device, its window, its loaded image.
- A person sits at the program and should see that Arkitekt is connected and who is calling it.

If nothing else owns the process, a plain [device](/docs/guides/app-kinds/device) or
[plugin](/docs/guides/app-kinds/plugin) is simpler.

## The shape: beside any program

`run_detached` starts the app in the background and returns at once. Your program hands it its own
objects as the app context, and listens to what happens:

```python
from arkitekt import App, run_detached

app = App("my-instrument", "0.1.0", app_context=Instrument)   # Instrument: your existing class


@app.action
def set_flow(pump: str, ml_per_min: float, instrument: Instrument) -> None:
    """Set Flow"""
    instrument.set_flow(pump, ml_per_min)


instrument = Instrument(...)                  # the program's own object
running = run_detached(
    app,
    context=instrument,                       # every action asking for Instrument gets this one
    headless=True,
    device_code_hook=show_login_in_my_ui,     # the login link, in your interface
    connection_listener=show_connection,      # connecting, connected, lost, …
    task_listener=show_who_called,            # a task assigned, done, failed
)
...                                           # the program goes on with its own loop
running.cancel()                              # on shutdown, from any thread
```

The listeners are called on the run's own thread. In a GUI, hand what they receive to the toolkit
the way it expects, for example through a Qt signal.

## The shape: a Qt window

For a Qt program, `arkitekt.qt` (the `qt` extra) has a declaration whose actions can run in the Qt
loop, and a bar that logs in and starts the app at a click:

```python
from qtpy import QtWidgets

from arkitekt import connect
from arkitekt.qt import MagicBar, QtApp


class Window(QtWidgets.QWidget):
    def __init__(self) -> None:
        super().__init__()
        self.runtime = connect(app, provide=True)
        self.bar = MagicBar(self.runtime, context=self)


app = QtApp("my-viewer", app_context=Window)


@app.register_in_qt_loop
def show_message(text: str, window: Window) -> str:
    """Show Message"""
    ...                                        # runs where widgets live
```

`arkitekt create my-viewer --template qt` writes a complete one.

## The shape: a JVM host

The [Kotlin client](/docs/guides/kotlin) exists for exactly this pattern: it runs an agent inside
Fiji's own JVM, so ImageJ operations become actions with no second process. It has actions, state,
locks and bloks, but no workflows.

## What to watch

- **Don't put `run(app)` on a thread.** `run_detached` is that, plus a way to stop it, to know its
  state and to cancel a login nobody approved.
- **The program is the truth.** When someone changes the instrument at the program itself, write
  the change to the published state from the program's own code. The state should be right no
  matter who changed the device. And the program's UI shows the published state rather than
  keeping its own copy (see [Anti-patterns](/docs/concepts/building/anti-patterns#ui-state)).
- **Give it a version of its own.** A login is stored per app identifier and version. Version the
  app by what it offers, not by the host program's release number.
