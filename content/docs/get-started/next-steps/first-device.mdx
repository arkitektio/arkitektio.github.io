A stage controller, a shutter or a pump often sits behind a microcontroller that cannot run Python.
Such a board can be an Arkitekt [agent](/docs/concepts/terminology#agent) of its own: it registers
actions that anyone in your organization can call from Orkestrator, a script or a workflow, and it
publishes live state, with no computer in between.

There is no separate embedded SDK. A microcontroller runs the same crates as a
[desktop Rust app](/docs/get-started/next-steps/first-rust-app), with the same `App`, `#[action]`
and `#[derive(State)]`. The crates are built without the standard library and run on
[embassy](https://embassy.dev), an async runtime for bare metal.

<Callout type="warn" title="Experimental">

The embedded stack is young and changes quickly. The demo below is the reference and the starting
point for your own firmware. [What is not there yet](/docs/reference/embedded#what-is-not-there-yet)
lists the gaps. Do not use it for safety-relevant hardware.

</Callout>

<Prerequisites>

- An **ESP32-S3** board (the demo targets the ESP32-S3-DevKitC-1) or a classic **ESP32**, with at
  least 4 MB of flash
- The Espressif Rust toolchain, installed with [`espup`](https://github.com/esp-rs/espup)
- A running hub, and Orkestrator on a computer with Bluetooth, to provision the device
- A Wi-Fi network (WPA2-Personal, or WPA2-Enterprise such as eduroam) from which the device can
  reach your Arkitekt server

</Prerequisites>

## The demo

[`esp32-embassy-demo`](https://github.com/arkitektio/esp32-embassy-demo) is a complete firmware
that turns an ESP32 into an agent. Everything on the board is Rust, with no ESP-IDF or C SDK
underneath. Its actions and states exercise every part of the path:

| | What it does |
|---|---|
| `echo` | Returns the text it was given. Proves a task makes the round trip. |
| `free_heap` | Returns the free heap in KiB |
| `set_led` | Switches the board's RGB LED on or off (ESP32-S3) |
| `set_led_color` | Lights the LED in a colour, from red, green and blue values (ESP32-S3) |
| `Sensors` state | The chip temperature, the Wi-Fi signal, the free heap and how often the BOOT button was pressed |
| `Led` state | Whether the LED is on, and its colour |

Once it runs, call `set_led_color` from Orkestrator and watch the `Led` state follow, or press the
BOOT button and see `presses` count up. That is the model from
[shared concepts](/docs/concepts/building/shared-concepts), on a chip the size of a stamp.

## From power-on to the first task

1. **Identity.** The device derives its id from its MAC address, so it keeps the same identity
   across reflashes.
2. **Provisioning over Bluetooth.** It advertises itself as `ARKITEKT-xxxx`. In Orkestrator, under
   **Lok → Provision a device**, you pick it. Orkestrator issues a key for it and sends the Wi-Fi
   credentials, the address of your deployment and the key in one document, which the device
   stores in flash.
3. **Wi-Fi.** It joins the network, including enterprise networks such as eduroam.
4. **Clock.** It sets its clock over SNTP, because a certificate cannot be checked without the date.
5. **Login.** It logs in with the key it was given. The key stands in for the approval a person
   gives a desktop app in the browser.
6. **Agent.** It opens the [agent socket](/docs/reference/protocols/agent), registers its actions and
   states, and waits for tasks.
7. **Bluetooth off.** Five seconds after registering, Bluetooth is switched off and its memory is
   given back to the app.

Hold the BOOT button for 5 seconds while the device starts to erase its configuration and login and
return to step 2.

## How the actions are written

The actions are ordinary `#[action]` functions, as in
[Your first Rust app](/docs/get-started/next-steps/first-rust-app):

```rust
/// Free heap
///
/// How much heap the device has left, in KiB.
///
/// # Returns
/// Free heap in KiB
#[action]
async fn free_heap() -> i64 {
    (esp_alloc::HEAP.free() / 1024) as i64
}
```

State is a struct deriving `State`, and an action that changes hardware updates it:

```rust
/// The board's LED, as the actions left it.
#[derive(Clone, Debug, Serialize, Deserialize, State)]
#[state(name = "Led")]
struct LedState {
    /// Whether the LED is on
    on: bool,
    /// The colour it shows when on, as #rrggbb
    color: String,
}

/// LED
///
/// Switches the board's LED on or off.
///
/// # Arguments
/// * `on` - Whether the LED should be on
///
/// # Returns
/// Whether the LED is on now
#[action]
async fn set_led(on: bool, state: StateMut<LedState>) -> anyhow::Result<bool> {
    led::set(on);                      // drive the pin
    state.set(LedState::now())?;       // publish what it is now
    Ok(state.read(|led| led.on))
}
```

A **background hook** reads the chip once a second and keeps the `Sensors` state current. It
publishes only when a value moved by a meaningful step (half a degree, 3 dB), so sensor noise does
not turn into a stream of patches.

The app is declared as on a desktop:

```rust
let app = App::new("live.arkitekt.esp32-embassy", "1")
    .action(echo)
    .action(free_heap)
    .state(sensors::read())
    .background(sensors::report)
    .state(LedState::now())
    .action(set_led)
    .action(set_led_color);
```

What differs is how it runs. A desktop app calls `run(app)`. A board has no operating system to
provide a network, a clock or randomness, so the firmware hands those over as a `Board` and connects
on it:

```rust
let board = Board { host: &HOST, tcp, dns, verify: verify() };
let runtime = Runtime::connect(board, app, options).await?;
runtime.serve().await?;
```

## Build and flash

Install the toolchain once, then build, flash and open the serial monitor in one step:

```sh
espup install
. ~/export-esp.sh

cargo esp32s3     # an ESP32-S3
cargo esp32       # a classic ESP32
```

The image is about 2.4 MB. Provision the device from Orkestrator under
**Lok → Provision a device**. It appears under **Apps** with its actions and its two states.

<Callout type="info" title="Until the crates are published">

The demo depends on sibling checkouts: the provisioning crate from
[`arkitekt-esp32-rs`](https://github.com/arkitektio/arkitekt-esp32-rs), and unreleased versions of
the arkirust crates. Its
[README](https://github.com/arkitektio/esp32-embassy-demo#build-and-flash) says which repositories
to place side by side.

</Callout>

<Quiz>
  <Question q="Which client does an embedded device use?">
    The Rust client. A microcontroller runs the same crates as a desktop Rust app, with the same `App`, `#[action]` and `#[derive(State)]`, built without the standard library on embassy.
  </Question>
  <Question q="How does a device with no screen or browser get authorized?">
    It is provisioned over Bluetooth from Orkestrator, which issues a key and sends it together with the Wi-Fi credentials and the deployment's address. The device logs in with that key.
  </Question>
  <Question q="What differs between a desktop Rust app and the firmware?">
    Not the actions or the states, but how the app is run: the firmware passes the network, clock and randomness of the board in as a `Board` and calls `Runtime::connect` on it, where a desktop app calls `run(app)`.
  </Question>
