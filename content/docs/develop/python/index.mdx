`arkitekt` is the Python client for Arkitekt and its reference implementation: every platform
feature reaches Python first. This section covers version 19 and later, on Python 3.11 or newer.
Porting an older app? See [Legacy](/docs/legacy), or [What changed in 19](#what-changed-in-19) if
you come from 18.

You use the package in one of two directions:

| Direction | You write | Entry point |
|---|---|---|
| **Offer** actions others can call | an `App` with `@app.action` functions | `run(app)` or `arkitekt run dev` |
| **Call** the platform | a script or notebook | `connect(Mikro, …)` |

Most of the guides are about offering actions. Calling is covered in
[Scripts & notebooks](/docs/develop/python/scripts).

## Install

```bash tab="uv"
uv add "arkitekt[all]"
```

```bash tab="pip"
pip install "arkitekt[all]"
```

To start a new app with nothing installed, run `uvx arkitekt create my-app`.
[Installation](/docs/develop/python/installation) lists the extras and how the package finds your
server. You need a server to connect to: [join one](/docs/get-started/join/super-quick) or
[start your own](/docs/get-started/deployment/first-hub).

## Core concepts [#core-concepts]

The words used throughout the guides, and what each looks like in Python. The
[terminology](/docs/concepts/terminology) defines them for the whole platform.

| Term | In Python |
|---|---|
| **App** | `App("hello", "0.1.0")`: a declaration of who the app is and what it offers. It connects nothing. |
| **Action** | A function decorated with `@app.action`. Its parameters and return type become ports. |
| **Implementation** | Your function, in this app and version, serving an action. |
| **Agent** | The process started by `run(app)`, which receives tasks. |
| **Task** | One run of an action. A parameter annotated `Task` gives you the running task. |
| **Structure** | A type passed by reference, such as Mikro's `Volume`: only its id travels. |
| **State** | An `@app.state` class, published live as it changes. |

### Action and implementation [#action-and-implementation]

The action is the abstract "what", defined by its ports. The implementation is your function. Two
apps can implement the same action, and the platform picks one when a task is created.
`@app.action(...)` takes these options:

| Option | Meaning |
|---|---|
| `name=` | Override the action's name (defaults to the function name) |
| `effects=` | What running it again would do: [effects](/docs/develop/python/durable-execution#effects) |
| `policy=` | What happens to a running task if the agent loses its connection: [disconnect policy](/docs/develop/python/durable-execution#disconnect-policy) |
| `concurrency=` | `"serial"` (default) or `"parallel"` runs of this action on one agent |
| `locks=` | Named locks a task must hold while it runs |
| `widgets=`, `port_groups=`, `validators=` | Per-port UI widgets, grouping and validation |

### The running task

Annotate a parameter with `Task` to get the running task. Each method has an async twin
(`await task.aprogress(...)`), and `Task.local()` is a stand-in for tests.

| Method | Purpose |
|---|---|
| `task.log(message, level)`, `task.progress(percent, message)` | Logs and progress, shown live |
| `task.pausepoint()` | A point where the task pauses if someone paused it |
| `task.now()`, `task.random()`, `task.sleep()`, `task.record(fn)` | Outside values, recorded for [durable execution](/docs/develop/python/durable-execution) |
| `task.retry(...)`, `task.hold(...)`, `task.guard(...)` | Deciding about a [lost step](/docs/develop/python/durable-execution#handling-a-lost-step) |
| `task.id`, `task.user`, `task.org` | Who and what this task is |

### Injection by annotation [#injection-by-annotation]

Some parameters are filled by the runtime, not the caller. They are recognized by their annotation
and are not ports:

| Annotated with | Injected value |
|---|---|
| `Task` | The running task |
| A client (`Mikro`, `Fluss`, `Rekuest`, …) | The connected client. The annotation also makes the app use that client |
| An `@app.state` class | The app's live state |
| An `@app.context` class | The shared context built by a startup hook |
| The class passed as `App(app_context=...)` | The value passed to `run(app, context=...)` |
| An `@app.declare` protocol | A proxy that calls another app's actions (workflows only) |

### Sync or async? [#sync-or-async]

Both work for actions, hooks and workflows. Use `async def` when your code awaits I/O or async
clients, and `def` for CPU-bound or blocking code, which runs in a worker thread. Every client and
task method has both forms, `x(...)` and `await ax(...)`. See
[Sync and async with koil](/docs/develop/python/koil).

### Disconnect policy [#disconnect-policy]

By default a task keeps running when its agent loses the connection.
`policy=CancelOnDisconnect(grace=...)` stops it instead. See
[Disconnect policy](/docs/develop/python/durable-execution#disconnect-policy).

## What changed in 19 [#what-changed-in-19]

In 19 an app is a set of declarations, assembled when it is run or inspected. Porting from 18:

| In 18 | In 19 |
|---|---|
| `App(..., services=[mikro_service])` | `App(...)`. The `Mikro` annotation (or a Mikro structure) is enough |
| `app.service(elektro_service)` | Nothing, or `App(clients=[Elektro])` if no annotation names it |
| `App(providers=...)`, `app.provider(...)` | `App(provider=...)` |
| `App(registry=merge(a, b))`, `app.merge(...)` | `App(include=[...])`, `app.include(...)` |
| `easy("name", mikro_service)`, `aeasy(...)` | `connect(Mikro)` (`with` or `async with`), `identifier="name"` to name it |
| `interactive("name", mikro_service)` | `connect(Mikro).enter()` |
| `rekuest_service` / `rekuest_caller_service` in a script | `connect(RekuestCaller)` (`from rekuest.client.client import RekuestCaller`) |
| A bad declaration raises at the decorator | Every problem is raised together, as `AppDeclarationError`, at assembly |
| `arkitekt inspect services`, `gen init --service` | `arkitekt inspect clients`, `gen init --client` |
| `arkitekt.testing.service_images`, `RunSnapshot.services` | `client_images`, `RunSnapshot.clients` |

`run`, `arun`, `serve`, `connect(app)` and `run_detached` also take `clients=[...]`: client
instances to use instead of building them, such as a fake in a test.
