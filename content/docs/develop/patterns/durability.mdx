Lab work runs for hours across several machines, and any of them can crash, reboot or lose power.
Arkitekt's answer is **durable execution**, built on three principles:

1. **Finished work is never redone.**
2. **Unknown outcomes are not guessed.** If an agent dies mid-task, nobody knows whether the work
   happened, and the platform says so. The server re-runs nothing on its own, except work no agent
   ever picked up.
3. **Whoever has the context decides**: the workflow's code, the calling script or a person.

For the Python API and examples, see [Durable execution](/docs/develop/python/durable-execution).

## The patterns

- **Event-sourced workflows, replayed deterministically**, as in engines such as Temporal. Every call
  and every outside value is recorded, and a resumed workflow gets the recorded answers back.
- **Idempotent child calls.** A replayed call finds its existing child task by its call key.
- **At-least-once delivery, deduplicated.** Agents resend what the server has not acknowledged, and
  the server ignores duplicates.
- **Only workflows may call.** A plain action that called others and died would leave no record of
  which calls finished. Each implementation is either `PLAIN` or `WORKFLOW`.
- **Explicit compensation.** The platform never retries a started step. The workflow or a person
  decides.

## When an agent dies

| What died | Who handles it | Outcome |
|---|---|---|
| the agent of a plain task | the caller | the task ends **LOST**, and the caller gets `AgentLost` |
| the agent of a workflow | the server | the workflow is **resumed** from its journal |
| the agent of a step inside a workflow | the workflow's code | the step's call raises `AgentLost` there |
| a caller (UI, script) | nobody | nothing: a caller disconnecting is not a failure |

An agent counts as dead when it stays disconnected past the server's grace window, or at once when a
new process takes it over.

**LOST** is a final [task state](/docs/concepts/tasks#states) meaning the outcome is unknown.
It carries whether the task ever started (if not, sending it again is safe), its last progress and its
effects claim. A result that arrives later is kept but never replaces it.

## Effects [#effects]

Each implementation claims what running it again would do to the world:

| `Effects` | Running it again… | Example |
|---|---|---|
| `NONE` | changes nothing | count cells |
| `REPEATABLE` | leaves the same state as running it once | rename a dataset |
| `UNKNOWN` (default) | nobody has said | store a new label dataset |
| `IRREVERSIBLE` | happens again, in the real world | dispense liquid |

The claim is information for whoever decides about a lost task. Neither the server nor the SDK's
retry helper acts on it.

## What is persisted where [#what-is-persisted-where]

**On the agent**, a journal of everything it reports, from task events and logs to recorded effects
and state patches, numbered without gaps. It is a SQLite file, by default
`.arkitekt/rekuest_journal.db` in the app's working directory or `$REKUEST_JOURNAL_PATH`. Entries
stay until the server acknowledges them, so a resumed workflow also gets what the dead process
recorded but never sent.

**On the server**, Rekuest's task history: each task's events, with every recorded effect unique per
key; its child tasks, unique per call key; a hash of the implementation's source; and a resume
counter.

## How a workflow is replayed [#replay]

Every value that came from outside the code must come back identical on replay, so two kinds are
recorded under keys. **Effects** are time (`task.now()`), randomness (`task.random()`), a sleep's
deadline, anything wrapped in `task.record(fn)` and the outcome of a hold. **Calls** are keyed by
target, argument hash and occurrence; graph workflows from Orkestrator key them by node.

When the agent dies, Rekuest requeues the task. If the source hash changed, or the task was already
resumed three times, it ends LOST. Otherwise a new process runs it from the top: effect helpers return
their recorded values, a finished call returns its result without running, and a running call
continues live. A key that now names a different action or kind of value raises
`NonDeterministicWorkflow`.

## Deciding about a lost step

Inside a workflow, a lost step raises `AgentLost`, and the SDK offers three answers:

- **Retry**: automatic if the step never started, opt-in after that. It reacts to lost agents only.
- **Hold**: pause with a message so a person can check the real world and resume or cancel.
- **Guard** a dependency's published state: on resume, raise `StateChanged` if something else changed
  it while the workflow was down, or if that agent restarted.

## What it buys

| Guaranteed | Not guaranteed |
|---|---|
| A finished child call is never run again in the same workflow run | That a started but lost step did or did not take effect |
| A resumed workflow sees the same recorded time, randomness and values | That code outside `task` helpers and calls replays identically |
| Reports reach the server in order, despite reconnects and restarts | That a workflow survives a change to its own source |
| LOST is final | Automatic retries of started work |
| A plain task's loss reaches its caller with what is known | Idempotency of your actions: `effects` is a claim |

## What it costs

- **Deterministic workflow code.** A `time.time()` or a file read in a workflow breaks replay.
- **Workflows are pinned to their code**, though only the workflow function itself is hashed: a change
  to a helper it calls goes unnoticed.
- **Plain tasks are not resumed.** Long work that must survive a crash has to be a workflow.
- **At most three resumes**, and a resumed run reports its progress, logs and yields again.
- **Guards** see only published state, need a dependency resolved to one agent, and do not watch while
  the workflow runs.
- **The journal lives on the agent's disk.** If the disk is lost, unsent values are taken anew. Give
  long-running workflow agents persistent storage for their `.arkitekt` folder.
