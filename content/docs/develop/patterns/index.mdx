Arkitekt's API has rules that can look arbitrary at first. A client is a parameter, not a global.
A plain action may not call another one. An image is never returned, only a reference to it. A
position is published, never returned by a getter. Each of these follows from a well-known
software design pattern, chosen because labs have a few hard requirements: work runs across many
machines, some of it moves real hardware, any machine can die, and every result should say where it
came from.

This section names those patterns, shows where you meet them in the API, and says honestly what
each one costs. It is the "why" behind [Shared concepts](/docs/develop/shared-concepts) and the
reasons behind the [anti-patterns](/docs/develop/anti-patterns).

| Pattern | You meet it as | It buys | It costs |
|---|---|---|---|
| [Declare, then assemble](/docs/develop/patterns/declaration) | `App(...)` and decorators, no manifest file | Inspecting, checking and packaging an app without running it | Nothing happens at import, by design |
| [Dependency injection](/docs/develop/patterns/dependency-injection) | `task: Task`, `mikro: Mikro`, `stage: Stage` parameters | Functions with no connection code, testable with fakes | Injection is by type, so types must be exact |
| [Stateless actions, explicit state](/docs/develop/patterns/stateless-execution) | Arguments in, result out; `@app.context`, `@app.state` | Any agent can run a task; retries and routing are possible | Long-lived things must be declared, not kept in globals |
| [Pass by reference](/docs/develop/patterns/pass-by-reference) | `Volume`, `SingleChannelImage`, memory structures | Large data never travels between apps | An extra fetch, and a store everyone can reach |
| [Observable state](/docs/develop/patterns/observable-state) | `@app.state`, bloks binding `self.Stage.x_um` | No polling, one truth per device, a history of it | Every update is a frame: state must stay small and slow |
| [Durable execution](/docs/develop/patterns/durability) | `@app.workflow`, `task.now()`, `AgentLost`, `effects=` | Workflows that survive crashes without redoing finished work | Deterministic workflow code; decisions about lost steps are yours |
| [Contracts and late binding](/docs/develop/patterns/contracts) | Actions vs implementations, `@app.declare` protocols | Swap, upgrade or duplicate apps without changing callers | Matching is by signature, so signatures are a promise |
| [Outbound agents, actors inside](/docs/develop/patterns/agents-and-actors) | `run(app)`, `concurrency=`, `locks=` | Runs behind any firewall; no two tasks fight over a device | Tasks of one action queue by default |

## One idea underneath

Most of these come from one decision: **the platform, not your code, owns the plumbing.** Your
function says what it needs and what it produces. Where the data lives, which agent runs the task,
how the login works, what happens on a crash and who sees the result are the platform's business,
and it can only take them on if your code does not do them itself.

That is also why the patterns hold in every language. The [Python](/docs/develop/python),
[Rust](/docs/develop/first-rust-app) and [Kotlin](/docs/develop/kotlin) clients spell them
differently, but they speak one protocol, and the protocol is where the patterns live.
