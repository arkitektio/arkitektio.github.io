Arkitekt has clients in several languages, and they all describe the same things to the platform,
because the platform speaks one protocol. Once you know the model in one language, the others are a
change of syntax.

| Concept | What it is | Who sees it |
|---|---|---|
| **App** | A declaration: who the program is and what it offers | The platform, when the app connects |
| **Action** | A function others can call, with typed inputs and outputs | Everyone in your organization |
| **Service** | A part of the platform the app uses, such as Mikro for images | The app's actions, as an injected client |
| **State** | A small set of values the app publishes as they change | The UI and other apps, live |
| **Blok** | A UI panel wired to actions and state | A person, in Orkestrator |

## The app and its lifecycle [#the-app]

An app is a **declaration**: an identifier, a version, the services it needs and what it offers.
Declaring it contacts nothing, so an app can be inspected, tested and packaged without a server.
Running it goes through the same steps in every language:

1. **Connect.** The first time, a person authorizes the app in a browser and approves the services it
   asks for. The credential is cached, so later runs connect straight away.
2. **Register.** The process becomes an [agent](/docs/concepts/apps-and-actions#agent) and tells the
   platform which actions, states and bloks it has.
3. **Start up.** When the agent starts providing, startup hooks run once, before the first task:
   open the device, load the model, set the initial state.
4. **Serve.** The agent waits for tasks and runs them until it is stopped.
5. **Shut down.** Shutdown hooks run on the way out and release what startup opened.

```python
from arkitekt import App, run

app = App("greeter", "0.1.0", description="Says hello")

# ... actions and states are declared on `app` ...

if __name__ == "__main__":
    run(app)   # connects, registers, serves until stopped
```

```rust
        .description("Says hello");
        // .action(..) and .state(..) are chained here

    run(app).await   // connects, registers, serves until stopped
}
```

```kotlin
    val app = App("greeter", "0.1.0")

    val connection = Runtime(app).connect("https://go.arkitekt.live")   // authorizes, registers
    connection.serve()                                                  // serves until cancelled
}
```

## Actions

An action is a plain function that the client turns into something the platform can call. You do not
write a schema; the client derives one from the function:

- **Parameters** become input [ports](/docs/concepts/workflows#port), and the **return type**
  becomes the output ports. The types drive validation, serialization and the form Orkestrator shows.
- The **doc comment** becomes the action's name, its description and a description for each port.
- A **default value** makes a port optional.

<Tabs items={["Python", "Rust", "Kotlin"]}>
<Tab value="Python">

```python
@app.action
def greet(name: str, times: int = 1) -> str:
    """Greet

    Says hello, possibly several times.
    """
    return " ".join([f"Hello {name}!"] * times)
```

</Tab>
<Tab value="Rust">

```rust
/// Greet
///
/// Says hello, possibly several times.
///
/// # Arguments
/// * `name` - Who to greet
/// * `times` - How often
#[action]
async fn greet(name: String, #[port(default = 1)] times: i64) -> String {
    format!("Hello {name}! ").repeat(times.max(1) as usize).trim_end().to_owned()
}

// let app = App::new("greeter", "0.1.0").action(greet);
```

</Tab>
<Tab value="Kotlin">

```kotlin
/**
 * Greet
 *
 * Says hello, possibly several times.
 *
 * @param name Who to greet
 * @param times How often
 */
@Action
fun greet(name: String, times: Int = 1): String = "Hello $name! ".repeat(times).trim()

// val app = App("greeter", "0.1.0").action(GreetAction)
```

</Tab>
</Tabs>

Rust and Kotlin derive the definition at compile time, Python when the decorator runs. All three
register the same definition, so a `Greet` written in Rust looks exactly like one written in Python.

Large data such as an image is a [structure](/docs/concepts/workflows#structure): only its id
travels, and the client turns it into an object for your function. A [service client](#services), a
[state](#state) or the running task is injected by the app and does not appear as a port.

## How calls are routed [#routing]

An action is the abstract "what", defined by its ports. Your function is one
[implementation](/docs/concepts/apps-and-actions#what-is-an-implementation) of it, and several apps can
implement the same action. A call, from a form, a script or a workflow, becomes a **task** in
[Rekuest](/docs/develop/internals/rekuest):

1. The caller names an action, or one specific implementation, and passes arguments. Rekuest checks
   them against the ports.
2. Rekuest resolves the implementation and everything it calls in turn, and freezes that tree onto
   the task, so every later call reaches the agents chosen at this moment.
3. The task is stored and handed to that agent. If the agent is offline, the task waits for it.
4. The agent runs the function and reports progress, logs and results, which reach the caller as
   they arrive.

Callers address an action, never a machine. If the agent dies mid-task, the task ends LOST (see
[Durable execution](/docs/develop/patterns/durability)).

## Services [#services]

Data lives in the platform's [services](/docs/develop/internals), such as
[Mikro](/docs/develop/internals/mikro) for images and [Kraph](/docs/develop/internals/kraph) for the
knowledge graph. Your code never holds a URL or a token for them:

1. **The app declares the service** by name (`live.arkitekt.mikro`). The person who authorizes the app
   approves that list.
2. **The server says where it lives** on this deployment
   ([service discovery](/docs/develop/internals/service-discovery)), so the same binary runs against a
   laptop and an institute's server.
3. **An action takes the client as a parameter.** The runtime builds it once per connection,
   authenticated as the app, and injects it.

Python infers the declaration from the type annotation (`mikro: Mikro`). Rust and Kotlin use
`.service(..)` and mark the parameter `#[inject]` or `@Inject`. Declaring a service also brings its
types, such as Mikro's images, as ports.

## State [#state]

A task lives for one call; the position of a stage lives as long as the app. **State** is a small
typed record the app publishes. When an action changes a field, the client sends a patch, and
Orkestrator and other apps see it live without polling.

<Tabs items={["Python", "Rust", "Kotlin"]}>
<Tab value="Python">

```python
@app.state
class CameraState:
    """What the camera is doing."""

    connected: bool = False
    frames: int = 0


@app.startup
def connect_camera() -> CameraState:
    return CameraState(connected=True)   # built once, before the first task


@app.action
def snap(state: CameraState) -> int:
    """Snap"""
    state.frames += 1                    # published as it changes
    return state.frames
```

</Tab>
<Tab value="Rust">

```rust
#[derive(Debug, Clone, Default, Serialize, Deserialize, State)]
#[state(name = "CameraState", locks = ["camera"])]
struct CameraState {
    /// Whether the camera is connected
    connected: bool,
    /// Frames acquired so far
    frames: i64,
}

#[action]
async fn snap(camera: StateMut<CameraState>) -> anyhow::Result<i64> {
    camera.update(|c| c.frames += 1)?;   // published as it changes
    Ok(camera.read(|c| c.frames))
}

let app = App::new("camera", "0.1.0")
    .state(CameraState::default())
    .startup(|startup| async move {      // runs once, before the first task
        startup.set_state(CameraState { connected: true, frames: 0 })?;
        Ok(())
    })
    .action(snap);
```

</Tab>
<Tab value="Kotlin">

```kotlin
@State(name = "CameraState", locks = ["camera"])
data class Camera(val connected: Boolean = false, val frames: Int = 0)

@Action
suspend fun snap(camera: StateMut<Camera>): Int {
    return camera.update { it.copy(frames = it.frames + 1) }.frames   // published as it changes
}

val app = App("camera", "0.1.0")
    .state(CameraState, Camera(connected = true))
    .action(SnapAction)
```

Kotlin has no startup hook yet, so the initial value is passed to `.state(…)`.

</Tab>
</Tabs>

Every action that takes the state gets the same instance, and a state can name locks an action must
hold to change it, so two tasks cannot move the same stage at once. Keep it to values a workflow could
guard on or a person could act on. Models and device handles go in a private context, fast data in a
stream ([Anti-patterns](/docs/develop/anti-patterns#frequency)).

## Bloks [#bloks]

A **blok** is a declarative UI panel the app contributes and Orkestrator renders. It is written in
BSX, which reads like JSX. `{self.CameraState.frames}` binds to a state, and
`onClick={self.snap() into snapping}` calls an action and names the call, so the panel can show
`snapping.running`:

```xml
<Blok kind="agent" context="panel">
  <Card>
    <CardHeader><CardTitle>Camera</CardTitle></CardHeader>
    <CardContent>
      <Text>{self.CameraState.frames} frames</Text>
      <Button onClick={self.snap() into snapping} disabled={snapping.running}>Snap</Button>
    </CardContent>
  </Card>
</Blok>
```

The source is the same in every language, and a blok refers to actions and states by name, so it
does not care which language implemented them. The platform refuses a blok that uses an action or
state the app does not declare (Rust and Kotlin rely on the server for this check, which needs
rekuest-server 21.4 or newer). View state, such as a slider before Apply, goes in a `<local>`, never a
copy of the app's state ([Anti-patterns](/docs/develop/anti-patterns#ui-state)). The
component catalog is in [Bloks: UIs from JSX](/docs/develop/python/bloks).

## What each client supports [#what-each-client-supports]

| | Python | Rust | Kotlin |
|---|---|---|---|
| **App**: declare, connect, serve | yes | yes | yes |
| **Actions** from functions | `@app.action` | `#[action]` | `@Action` |
| Structures by id | yes | yes | yes |
| **Services** declared and injected | the annotation (`clients=[...]` for extras) | `.service(..)` and `#[inject]` | `.service(..)` and `@Inject` |
| Ready-made Mikro client | yes | yes (array datasets) | not yet |
| Progress and logs from a task | yes | yes | yes |
| **State**, published live | `@app.state` | `#[derive(State)]` | `@State` |
| Startup, background, shutdown hooks | yes | yes | not yet |
| Locks | yes | yes | yes |
| **Bloks** declared on the app | `app.blok(...)` | `.blok(..)` | `.blok(..)` |
| Workflows (actions calling actions) | yes | not yet | not yet |
